PD-mux 실험 검토

앞으로 VESSL Cloud의 A100에서 무엇을 어떤 순서로 재며, 그 결과가 논문에서 어떤 역할을 하는지, 비용은 얼마인지, 어떤 결정이 남았는지를 정리했다. 연구 배경·hybrid 특성·워크로드 지도·동작 시나리오는 짝 페이지 Hybrid PD-mux 로드맵에 있다. 내부 문서의 카드 번호·판정 코드는 맨 아래 대응표에만 남겼다.

기준일 2026-09-27실행 환경 VESSL Cloud · A100 80GB 1장 · us-west-2GPU 요금 $1.55/시간지금까지 VESSL 지출 $0
이 페이지의 성격. 계획과 예측이지 측정 결과가 아니다. 예측값은 전부 "아직 재지 않은 제안"이며, 결과를 본 뒤에 기준을 바꾸지 않는다는 원칙 아래 사전 등록을 거쳐야 실행된다. 내용은 2026-09-27 내부 감사(claims-auditor)에서 지적된 과장과 사실 오류를 고친 판이다.

1. 지금까지 확정된 것 (옛 환경 KISTI A100, 재측정 불필요)

세 가지 결론이 실제 서빙 측정으로 확정됐다. 다만 전부 옛 환경(KISTI의 A100, 모델 1종 Zamba2-2.7B 중심)에서 얻은 것이라, 논문에서는 "그 환경의 결과"로 표기하고 새 환경 수치와 섞지 않는다.

① 분할 서빙은 기본 서빙보다 낫다

prefill과 decode를 분리해 돌리면(PD-mux) 한 배치에 섞어 돌리는 기본 방식(fused)보다 꼬리 지연 기준 goodput이 좋았다. 단, 이것은 "PD-mux 기능 묶음을 켠 효과"이지 "SM을 나눈 것 자체의 효과"라고 증명된 것은 아니다. 운영 설정(CUDA graph 사용)에서 확인된 모델은 2종이다.

② 층 종류별로 잘게 나누는 방식은 안 된다

attention 층과 SSM 층 경계마다 SM 배분을 바꾸는 방식은, 경계마다 GPU를 비워야 하고 CUDA graph(운영 속도의 핵심 최적화)와 양립하지 않아 decode 지연이 42→124 ms로 나빠졌다. 최적화해도 85 ms. 배분값을 미리 정해 둬도 실행 중 비용은 그대로다. 이 수치는 CUDA graph를 끈 상태에서 잰 것이라 크기가 아니라 방향으로 인용한다. 선행(MuxWise·Bullet)이 논문에서 쓰는 "층 단위 prefill 진행량 + SM 배분 동시 조절"은 시험하지 않았으므로 이 결과가 그 방식을 반증하지 않는다.

③ 실시간 조절은 고정 배분을 못 이긴다

부하를 보며 배분을 바꾸는 반응형 제어는, 부하가 변하는 trace에서도 "decode 쪽에 넉넉히 준 고정 배분"을 넘지 못했다(4회 이상 반복, 느슨한 SLO와 빡빡한 SLO 양쪽). 원인은 전환 비용이 아니라 위치 선정 실패와 연쇄 효과다: decode가 SM을 적게 받으면 토큰 간격이 늘고, 배치가 정체되고, 새 요청 입장이 막혀 첫 토큰 지연이 폭발한다. 이 결론은 "하나의 실행 루프가 두 단계를 함께 관리하는 반응형 제어"에 한정된다. 기준점(decode 최소 SM·워크로드별 최적)을 모른 채 움직인 조절기의 결과이며, 도달 가능한 상한이 아니다.

실무 권고(확정): 최고 decode 부하 기준으로 decode 쪽에 넉넉한 고정 배분을 쓴다. 검증된 모델 프로파일이 없으면 엔진 기본 배분 선택기(decode 배치 크기 문턱 표, agnostic)를 쓴다.

2. 실행 단계

GPU가 1장이라 순서대로 돈다. 2단계를 통과하기 전에는 어떤 본 실험도 제출하지 않는다. 비용은 GPU 시간(GPU-h)과 달러이며, 옛 환경의 경험값을 옮긴 추정치다.

0단계

로컬 준비

진행 중GPU 0 · $0

VESSL에서 바로 돌 수 있는 실행 환경을 내 PC에서 완성한다.

하는 일

  • 실행 이미지(컨테이너) 빌드 — 완료. VESSL 기본 이미지 위에 우리 엔진(SGLang v0.5.10 + 패치)을 얹었고, 패키지 147개 중 138개가 옛 환경과 같은 버전이다.
  • 이미지를 올릴 저장소(레지스트리) 결정 후 업로드 — 첫 업로드는 약 9 GB 이상.
  • 실행 시작 스크립트: GPU·드라이버·클럭 기록, 결과 복사, 체크섬 생성.

통과 기준

  • 이미지 식별자(digest)가 확정되고, 컨테이너 안에서 CPU 회귀 테스트가 로컬과 같은 결과를 낸다(신규 실패 0 — 확인됨).
1단계

VESSL 환경 만들기

필수CPU 2–4시간 · 약 $0.5–1 + 저장소 월 $6–9

계정·저장소·선불 크레딧을 만들고, GPU 없는 작업 공간에서 모델과 데이터를 미리 올려 둔다.

하는 일

  • CLI 설치·로그인, SSH 키, 저장소 2개(빠른 클러스터 저장소 = 실행 중 기록용, 오브젝트 저장소 = 결과 회수용).
  • CPU 전용 작업 공간에서 모델(Nano-9B, 17.8 GB)·요청 trace를 내려받아 저장소에 둔다. 한국↔미국 서부 전송은 느리므로 큰 파일은 VESSL 안에서 받는다.
  • 선택한 예산만큼만 크레딧을 충전한다. 잔액이 0 이하면 작업 생성이 막히므로 이것이 사실상 지출 상한이 된다.

통과 기준

  • A100 1장 전체를 주는 사양(일부만 주는 MIG 아님)과 CPU 전용 사양이 us-west-2에 있다.
  • 모델 파일의 해시가 고정 버전과 일치한다.
2단계

GPU 확인 — 분할이 실제로 되는가

로드맵 그림1 ②필수 · 실패 시 중단GPU 0.3–0.4시간 · 약 $2–4

이 GPU에서 우리가 쓰는 배분값이 실제로 그대로 잡히는지, 그리고 결과를 끝까지 내 PC로 가져올 수 있는지 확인한다.

하는 일

  • 배분값 4종(92/16, 84/24, 74/34, 64/44)마다 실제로 돈 SM 수가 요청값과 같은지 확인. 두 묶음이 겹치지 않는지, CUDA graph를 켜도 격리가 유지되는지 확인.
  • 모델을 띄워 짧은 요청이 왕복하는지 확인(부팅 스모크).
  • 작업 1개를 끝까지 돌려 결과 복사 → 다운로드 → 체크섬 대조까지 실증. 이때 이미지 내려받기·모델 로드 시간을 재서 예산 추정을 갱신한다.

통과 / 중단

  • 통과: 요청값 = 실측값, 겹침 없음, 격리 유지, 체크섬 일치.
  • 중단: 실측이 다르거나 겹치면 여기서 멈춘다. 그 자체가 "환경을 옮기면 분할이 달라진다"는 결과이며, 배분표를 다시 설계해야 한다.
3단계

기초 측정 — 곡선과 한계

로드맵 그림1 ① ③ ⑤필수GPU 2.2–3.3시간 · 약 $3.5–5

이후 모든 실험이 기준으로 삼을 두 가지를 잰다: decode가 SM 수에 얼마나 민감한가, 그리고 이 설정의 처리 한계는 얼마인가.

채워야 할 측정 공백 — decode 속도 vs 문맥 길이 × SM 수. hybrid 특성이 시스템에 드러나는 핵심 곡선(attention 4층의 몫이 문맥과 함께 커져 decode에 필요한 SM이 움직이는가)인데, 지금 쓸 수 있는 측정이 없다. 옛 값은 계측 결함 3건으로 인용 금지이고, 운영 설정(CUDA graph ON) 측정은 존재하지 않는다. 3-a가 이 곡선을 처음 잰다. 모델 구조 때문이라고 말하려면 구조가 다른 모델 2–3종이 필요하다.

3-a. decode 속도 곡선 (0.8–1.5 GPU-h)

  • decode만 돌리며 SM 수 × 배치 크기 × 문맥 길이를 바꿔 한 step 시간을 잰다. CUDA graph를 켠 운영 설정에서.
  • 배분을 바꿀 때 드는 시간(GPU를 비우는 비용, 그동안 놀게 되는 SM)도 함께 잰다.
  • 이것은 성분 측정이다. "그러니 분할 유지가 유리하다" 같은 정책 결론은 여기서 끌어내지 않는다.

3-b. 처리 한계 (1.4–1.8 GPU-h)

  • 짧은 입력(256 토큰 입력/512 출력)과 긴 입력(8192/64) 두 shape에서 초당 몇 요청까지 받는지 잰다.
  • 옛 환경의 값(약 3.0 / 0.7 req/s)과 비슷하게 나와도 그것을 "같은 환경"의 근거로 쓰지 않는다. 우연한 일치일 수 있다.
결정

두 가지 판단 — 실험 재개 전에 사람이 정한다

사용자 + 감사GPU 0

① 옛 환경과 같다고 볼 것인가

  • 같다고 판정하면 옛 수치(배분표, 처리 한계, 2개 모델 결과)를 새 결과와 나란히 쓸 수 있다.
  • 다르다고 보면 4개 모델을 전부 VESSL에서 다시 재야 하고, 옛 결과는 "옛 환경"으로 따로 표기한다. 비용이 약 3 GPU-h 늘어난다.

② 분할 유지 검증 실험(E2)의 실행 승인

  • 이 실험은 이미 설계·감사(5회)가 끝나 있고 설계 자체는 유효하다. VESSL로 옮기는 데 필요한 것은 실행 경로 보정과 예산 재승인뿐이다.
  • 설계를 줄이면 감사를 처음부터 다시 받아야 하므로 줄이지 않는다. 예산 1.8 GPU-h(최악 2.3).
4단계

본 실험 — 논문에 들어갈 측정

로드맵 그림1 ④ ⑥ · 그림2필수GPU 5.2–8.4시간 · 약 $8–13

4-a. 동거인가, SM 수인가 (0.4–0.6 GPU-h)

  • 질문: 나눠 놓은 상태에서 decode가 느려지는 이유가 "SM을 적게 받아서"인가, "옆에서 prefill이 같이 돌아서"인가.
  • 방법: decode를 44 SM에 묶어 두고 prefill이 있을 때/없을 때를 비교한다. 계측 자체가 성능을 바꾸지 않는지 확인하는 대조군을 같은 작업 안에 둔다.
  • 기대(제안): "옆에서 돌아서" 쪽이면 decode 시간 비율 1.0–1.15배, "SM 수" 쪽이면 1.5–1.9배. 그 사이(1.15–1.5)면 둘 다 작용한다.
  • 추가 arm(제안): 앉을 자리 아래 고정 배분. 3-a로 잰 decode 최소 SM보다 적게 준 고정 배분 1점을 같은 작업 안에 둔다. 옛 환경에서 본 굶김 연쇄(토큰 간격 상승 → 배치 정체 → 입장 차단)가 새 환경·Nano-9B에서 같은 순서로 나타나는지를 시간열로 확인한다. 이것이 기여 2(기전)와 기여 3(여유)을 인과로 잇는 고리다. 비용 약 0.2–0.3 GPU-h 추정(4-a 산정에 미포함), 4-a 등록 시 함께 등록. 3-a가 끝난 뒤에만 배분값을 정할 수 있다.
  • 의미: 일반 transformer에서는 선행 연구(MuxWise, Bullet)가 동거 간섭을 이미 보고했다. 우리 몫은 hybrid 모델에서의 재확인과, 동거 시간이 실제로 얼마나 되는지를 정의된 방식으로 세는 것이다(조사한 선행 4편에서는 집계값 보고가 확인되지 않음. "첫 측정"이라 쓰지 않는다).

4-b. 분할 유지 검증 (1.8 GPU-h, 최악 2.3)

  • 질문: "decode에 44 SM"이라고 설정하면 실제로 그 시간의 대부분이 44 SM에서 도는가.
  • 배경: 옛 환경에서 이 설정의 실제 점유가 소수에 불과했다는 것이 드러났다(prefill이 없을 때 GPU 전체로 돌아갔기 때문). 분할 유지 옵션이 이를 고치는지 확인한다.
  • 기대(등록됨): 유지 ON일 때 90% 이상, OFF일 때 20% 미만.
  • 의미: 이후 "고정 배분 D44"라고 말하는 모든 실험의 계측이 믿을 만한지를 정한다. 그 자체가 논문 기여는 아니다.

4-c. 추가 모델 2종 (3 GPU-h, 4종 전부면 약 6)

  • 질문: 분할 서빙이 기본 서빙보다 낫다는 결론이 NemotronH·Falcon-H1에서도 운영 설정으로 성립하는가.
  • 기대(제안): 부호와 자릿수가 기존 2모델과 같다. 갈리면 "모델에 따라 다르다"로 기록한다.
  • 의미: 이걸 해야 "hybrid 4모델에서 성립"이라고 쓸 수 있다. 위 결정 ①에서 "다르다"로 판정되면 옛 2모델도 다시 잰다.
5단계

조건부 확장 — 열릴 때만

로드맵 그림1 ⑦ · 그림3조건부GPU 20–30시간 · 약 $30–45

5-a. 워크로드별 최적 배분의 차이 (약 10 GPU-h, 별도 사전 등록)

  • 질문: 워크로드마다 가장 좋은 고정 배분이 다른가, 다르다면 "하나로 고정한 배분"과 얼마나 차이 나는가.
  • 이 차이가 3% 미만이면, 어떤 똑똑한 선택 방법을 만들어도 얻을 게 없다. 그래서 5-b를 하기 전에 먼저 잰다.
  • 설계 조건: 처리 한계 기준 부하 2점, 짧은 입력과 긴 입력 워크로드를 따로, 최적 배분을 고르는 작업과 평가하는 작업을 분리(고른 데이터로 평가하면 과대평가됨), 독립 작업 2회 × 반복 4회.
  • 먼저 GPU 없이 기존 자료로 "차이가 생길 만한 워크로드가 있는지"부터 확인한다.

5-b. 기준점을 바로잡은 배분 선택 (10–20 GPU-h, arm 추가 시 증가)

  • 질문: decode 최소 SM 곡선(3-a)과 워크로드별 최적(5-a)을 아는 배분 선택 — 특히 모델의 attention/SSM 구성 정보를 쓰는 것 — 이 고정 배분(B1)이나 일반 동적(B5)보다 goodput이 짝지은 신뢰구간 기준 3% 이상 좋고, 다른 영역에서 3% 넘게 나빠지지 않는가.
  • 조건: 5-a에서 차이가 확인되고, 별도 실행 구조(prefill·decode 각각 독립 스레드) 검증을 통과한 뒤에만.
  • 비교군: 고정(B1) · 일반 동적(B5) · 구조 정보(B6). [제안] agnostic 기준선 arm — MuxWise 저자들이 SGLang에 올린 기본 선택기(decode 배치 크기 문턱 → 배분 전환, 저자 주석상 임시 데모)를 108 SM용 표로 재현. 이미 잰 agnostic 기준선과 같은 기제이므로 새 방식이 아니다. 설정만으로 가능하지만 R2 정책·SLO 스케줄·분할 유지 옵션을 모두 꺼야 해 고정 arm과 노브가 여럿 동시에 움직인다 → 별도 사전 등록 + 규칙층 감사 후에만. 선행의 논문 방식(prefill 층 수를 decode step 시간에 맞춤 + 추정기)은 엔진 수정이라 현 계획 밖.
  • 비용: arm 하나당 반복 4회 × 독립 작업 2회가 늘어난다(10–20 GPU-h 산정에 미포함). 표의 행이 늘면 decode CUDA graph 메모리도 늘어 처리 한계를 arm별로 다시 재야 한다.
  • 솔직한 기대: 선행 연구(MuxWise)가 이미 워크로드별 배분표를 쓰고 있어서, 남는 차별점은 "구조 정보를 쓰느냐"와 hybrid 한정이다. 옛 환경 결과는 실시간 조절이 이길 영역이 좁다고 시사한다. 이기든 지든 결과가 남는다. 부하 인덱스 표 arm이 져도 "MuxWise가 졌다"고 쓰지 않는다(추정기·디스패처 없는 재현).

3. 논문에서의 기여

이미 확보옛 환경 결과, 그대로 사용

  • 층 종류별 세분 배분은 실패한다는 기전 규명. 왜 안 되는지(경계마다 GPU 비우기, CUDA graph와 충돌)까지 밝혔다. 한계: 우리 엔진·green context 방식·Zamba2 경로에 한정, 다른 분할 기술(libsmctrl)과 비교 없음. 선행(MuxWise·Bullet)의 논문 방식 — 층 단위 prefill 진행량과 SM 배분을 함께 조절 — 은 미시험이므로 반증 대상이 아니다.
  • 반응형 실시간 조절이 고정 배분을 못 넘는 이유. 전환 비용이 아니라 decode 굶김의 연쇄 때문이라는 것. 한계: 모델 1종, 하나의 루프가 두 단계를 관리하는 구조에 한정. 선행 연구(Bullet)가 반대 주장을 하는 부분은 검토 중. 시험한 조절기 계열의 실패이지 도달 가능한 상한이 아니며, 교정 사다리(3-a → 3-b → 5-a → 구조 분리 → 5-b)가 그 다음 질문이다.
  • 운영 가이드: 최고 decode 부하 기준의 고정 배분, 검증된 프로파일이 없으면 엔진 기본 선택기(agnostic). 이 규칙이 남기는 여유의 크기는 5-a가 잰다.

이번 실험으로 완성2–4단계

  • hybrid 모델 4종에서 분할 서빙이 기본 서빙보다 낫다(4-c). "분할 기능을 켠 효과"로만 서술하고 원인 귀속은 주장하지 않는다.
  • decode의 SM 민감도가 문맥 길이·부하에 따라 어떻게 변하는지(3-a). 모델 구조(attention 비율) 때문이라고 말하려면 구조가 다른 모델 2–3종을 더 재야 한다.
  • 동거 시간의 정의된 측정(4-a). 조사한 4편(DuetServe·MuxWise·Nexus·Bullet) 범위에서 정의·분모·규약을 갖춘 집계 추정량으로 이를 보고한 것은 확인되지 않는다(Bullet 그림 20a는 구성별 지속시간 타임라인으로 보여 주지만 집계값은 아니다). Bullet은 타임라인 그림으로, MuxWise는 다른 지표(활성 SM 비율)로 보여 준다.
  • 재배분 경계의 결정 표면(3-b·4-b 기록에서 추가 비용 없이). 기본 예산에서 짧은 입력은 prefill이 조각 1개라 prefill 도중 결정 지점이 없다. 옛 자료 재집계(판정 아님, 스크립트 미등록)를 VESSL 기록으로 재확인한다.
  • 방법론: 설정값이 아니라 실측값으로 배분을 검증해야 한다는 교훈(4-b), 환경을 옮길 때의 확인 절차(2단계).

조건부5단계가 열릴 때만

  • 기준점을 바로잡은 배분 선택이 고정 배분을 넘는가(5-b) — 구조 정보(B6) vs 일반 동적(B5) vs 고정(B1) vs [제안] 부하 인덱스 표. 성공해도 "실시간 조절"이 아니라 "워크로드에 맞는 고정 배분을 미리 잘 고르는 능력"으로 서술한다. 모델을 건너 일반화하려면 hold-out(구조가 다른 2–3종으로 맞추고 미사용 모델 예측)이 필요하다.
  • prefill·decode 독립 실행 구조가 간섭을 줄인다. 선행 연구(Bullet)와 겹치므로 hybrid 한정 + 간섭의 정량 기전으로 차별화해야 한다.

세부 항목과 근거 상태 (보고용 6절의 세 핵심 기여를 이루는 항목)

보고용 페이지의 기여 1은 아래 ①④와 3-b(처리 한계, 사실 기록), 기여 2는 ②③⑤⑧, 기여 3은 ⑥과 5-a 여유·⑨(조건부)에 대응한다. ⑦은 방법론으로 따로 둔다. 기여 2→3의 연결("정책은 앉을 자리를 알아야 한다"는 요구 조건)은 4-a 추가 arm에서 연쇄 신호가 재현될 때만 인과로 쓰고, 재현 전에는 해석으로만 쓴다. "어느 실험이 만드는가"는 이 페이지 2절의 단계 번호다.

기여한 줄 주장근거의 현재 상태어느 실험이 만드는가주장의 한계 (그대로 적을 것)
① hybrid 모델에서도 분할 서빙이 기본 서빙보다 낫다attention+SSM 모델 4종에서 PD-mux를 켜면 꼬리 goodput이 오른다옛 환경 운영 설정에서 2모델 확인(H3-f)4-c(추가 2모델), 3-b(처리 한계)"기능 묶음을 켠 효과"로만 서술. 원인이 SM 분할 자체인지는 미확립. 4모델 문장은 같은 환경에서 재거나 동등성 판정 후에만
② 층 종류 경계마다 GPU를 다시 나누는 방식은 실패한다는 기전attention/SSM 층 경계마다 SM을 바꾸면 GPU 비우기(격차의 약 절반)와 겹침 손실·CUDA graph 비양립으로 decode가 2–3배 느려지고, 운영 설정(graph ON)에는 들어갈 수 없다확정 — 현 구현 범위 한정 (H3-a·H3-c, 양쪽 graph OFF 측정)—(옛 환경 결과 사용)우리 엔진·green context·Zamba2 경로 한정. 선행(MuxWise·Bullet)이 논문에서 쓰는 방식 — 층 단위 prefill 진행량과 SM 배분을 함께 조절 — 은 시험하지 않았으므로 이 결과가 그 방식을 반증하지 않는다. 그 방식은 엔진 수정(조각 크기를 decode step 시간에 맞추기)이 필요해 현 계획 밖. libsmctrl 등 다른 분할 기술과 비교 없음
③ 반응형 실시간 조절이 고정 배분을 못 이기는 이유전환 비용이 아니라 decode 굶김이 대기열 폭발로 이어지는 연쇄 때문. 조절기가 "앉을 자리"(decode에 필요한 최소 SM)를 모른 채 움직인 결과확정 (H3-d·H3-e, 그림 3; 4회 이상 반복, 느슨·빡빡 SLO 양쪽)—(옛 환경 결과 사용). 새 환경 재현: 4-a 추가 arm(앉을 자리 아래 고정 배분)에서 연쇄 신호. 교정 사다리: 3-a(자리 곡선) → 3-b(한계) → 5-a(넘어야 할 선의 높이) → 구조 분리 검증 → 5-b시험한 조절기 계열(하나의 루프가 두 단계를 관리·SM 분할·반응형)과 모델 1종에 한정. 도달 가능한 상한이 아니다. 기준점을 알려 준 조절기가 이기는지는 ⑨의 열린 질문. 선행(Bullet)의 반대 주장은 열린 항목
④ hybrid decode의 SM 민감도가 문맥·부하에 따라 어떻게 변하는가문맥이 길수록 attention 4층이 decode 비용을 지배해 필요한 SM이 움직인다가설. 쓸 수 있는 측정 없음3-a(핵심), 3-b"모델 구조 때문"이라 말하려면 구조가 다른 모델 2–3종 필요. 옛 값은 계측 결함으로 인용 금지
⑤ 동거 시간의 정의된 측정과 "SM 수 vs 동거" 분해나눠 놓은 decode가 느린 이유를 SM 부족과 prefill 동거로 가르고, 동거 비율을 정의·분모·규약을 갖춘 집계값으로 센다옛 자료 재집계 있음(H3-g는 설정 배분의 실제 유지 비율; 동거 비율 집계 스크립트는 미등록이라 수치 인용 전 등록 필요). 분해 실험은 미실행4-a (4-b는 계측 타당성 확인용, 기여 아님)일반 transformer에서는 선행(MuxWise·Bullet)이 동거 간섭을 이미 보고. 조사한 4편 범위에서 정의된 집계값으로 보고한 것은 확인되지 않으나(Bullet 그림 20a는 구성별 지속시간 타임라인, 집계값 아님) "첫 측정"이라 쓰지 않음. 우리 몫은 hybrid 재확인 + 정의된 집계 + 워크로드별 값
⑥ 운영 가이드최고 decode 부하 기준으로 decode 쪽에 넉넉한 고정 배분; 검증된 프로파일이 없으면 엔진 기본 배분 선택기(decode 배치 크기 문턱 표, agnostic)확정(③에서 도출)3-b, 5-a(워크로드별 차이)prefix 캐시 OFF·문맥 16K 이하·짧은/긴 입력 분리 워크로드에 한정
⑦ 방법론배분은 설정값이 아니라 실측값으로 검증해야 하고(설정 D44의 실제 유지가 채팅형에서 등록 규약 a_r4 기준 13.64%), 환경을 옮길 때 확인 절차가 필요하며, 부하는 처리 한계의 비율로 정의한다옛 환경에서 두 번의 결론 번복으로 확인2단계, 3-b, 4-b—
⑧ 재배분 경계의 결정 표면 — 어디서 바꿀 수 있는가층 종류 경계는 불가(②), 조각·step 경계는 가능. 그러나 기본 예산에서 짧은 입력은 prefill이 조각 1개라 prefill 도중의 결정 지점이 없다 — 선행이 전제하는 "여러 층 단위 진행"이 채팅형에서는 서지 않는다옛 자료 재집계(판정 아님, 스크립트 미등록). 조각 수 규칙은 엔진 코드로 확정3-b·4-b의 기록에서 추가 비용 없이 재확인. 예산을 줄여 조각을 늘리는 비용(TTFT 2–4배 선례)은 5-a 전 확인 항목Nano-9B-v2·예산 65536·입력 256 기준. 예산은 서버 전역이라 요청별로 조각을 맞출 수 없음(엔진 수정 필요)
⑨ (조건부) 기준점을 바로잡은 배분 선택이 고정 배분을 넘는가decode 최소 SM 곡선(3-a)과 워크로드별 최적(5-a)을 아는 배분 선택 — 특히 attention/SSM 구성 정보를 쓰는 것 — 이 고정 배분(B1)·일반 동적(B5)보다 goodput이 짝지은 신뢰구간 기준 3% 이상 높고, 다른 영역에서 3% 넘게 나빠지지 않는가(부하 인덱스 arm은 등록되면 비교군으로 추가)미검증. 이기든 지든 결과가 남는다: 이기면 "기준점을 알면 동적이 산다", 지면 ③보다 강한 부정 결과5-a → 5-b. 비교군: 고정(B1)·일반 동적(B5)·구조 정보(B6)·[제안] agnostic 기준선(MuxWise 저자들이 SGLang에 올린 기본 선택기, 저자 주석상 임시 데모)을 108 SM 표로 재현한 arm(별도 사전 등록·감사 필요)성공해도 "실시간 조절"이 아니라 "워크로드에 맞는 배분을 미리 고르는 능력"으로 서술. 선행(MuxWise)이 워크로드별 표를 이미 씀 → 차별점은 구조 정보와 hybrid. 모델을 건너 일반화하려면 구조가 다른 2–3종으로 맞추고 미사용 모델로 예측(hold-out). 부하 인덱스 표 arm이 져도 "MuxWise가 졌다"고 쓰지 않음(추정기·디스패처 없는 재현)

투고 방향: 지금 자산과 2–4단계로는 "특성화 + 안 되는 이유의 규명 + 운영 가이드" 논문이 된다(MLSys·EuroSys·ATC 급). 5단계가 열리면 구성적 기여를 더할 수 있다.

6. 지켜야 할 원칙

환경 수치를 섞지 않는다 — 옛 환경(KISTI)과 새 환경(VESSL)의 수치는 결정 ①을 거치기 전에는 나란히 놓지 않는다. 처리 한계가 비슷하게 나와도 "같은 환경" 근거로 쓰지 않는다.
용량을 먼저 잰다 — 부하는 처리 한계의 비율로 정한다. 한계 근처에서는 첫 토큰 지연이 목표를 넘나들어 goodput이 3% 변동에 2배로 흔들리므로 그 구간을 피한다.
반복 4회 이상, 독립 작업 2회 이상 — 한 작업 안에서 여러 번 띄운 것은 독립 반복이 아니다(같은 노드·같은 상태). 비교군은 같은 작업 안에 번갈아 배치한다.
차이 3% 미만은 결론이 아니다 — 반복의 분산을 먼저 보고, 짝지은 신뢰구간이 0을 넘어야 헤드라인이 된다.
결과를 본 뒤 기준을 바꾸지 않는다 — 목표 SLO를 바꾸려면 그 SLO로 다시 조율해 다시 잰다. 기존 결과를 새 기준으로 다시 채점하지 않는다.
설정값이 아니라 실측값 — "44 SM을 줬다"는 설정이 아니라 기록에 남은 실제 점유로 확인한다. 이 원칙을 어겨 결론이 두 번 뒤집힌 적이 있다.
성분 측정에서 정책 결론을 끌어내지 않는다 — 3-a의 곡선만으로 "그러니 분할 유지가 낫다"고 쓰지 않는다. 정책 주장은 반드시 서빙 실측으로.
적용 범위를 적는다 — 이번 결론은 prefix 캐시 OFF, 문맥 16K 이하, 짧은/긴 입력을 분리한 합성 워크로드에 한정한다. 캐시를 켠 multi-turn 환경으로 옮겨 쓰지 않는다.
