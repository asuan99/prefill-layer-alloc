02

구조 플레이트 — 아홉 개를 같은 눈금으로

모든 그림이 같은 어휘를 쓴다. 아래 108 SM 레일은 항상 같은 자리에 있고, 그 위 상자들은 제어 평면, 아래 상자는 데이터 평면(running batch · KV/mamba pool)이다. 따라서 플레이트를 넘길 때 눈에 남는 것은 무엇이 달라졌는가 하나뿐이다.

fused — 비교 기준

기준선
plain · 무플래그

구조

prefill과 decode가 같은 event loop, 같은 running batch, 같은 108 SM에서 돈다. 유일한 완충은 chunked prefill이다.

측정

이 arm의 死因은 TPOT가 60 ms 임계를 넘는 것이다(Granite rate4 TPOT 61.21 ms). 그런데 cudagraph가 그 벽을 없앤다 — Zamba2 plain TPOT 62.70 → 13.51 ms, rate4 82.41 → 54.04 ms로 60 ms SLO를 통과한다.

판정

비교 기준으로만 쓴다.

미조율 baseline이다. fused가 졌다는 것이 "PD 분리가 옳다"를 뜻하지 않는다 — 관측된 실패모드(prefill 배치 stall)에 대해 이 arm은 조율된 적이 없다.
2026-09-01 추가 — chunked prefill을 비교군으로 세우려는 트랙(cp_baseline)은 정책 비교를 아직 한 건도 못 쟀다. 규칙층 적대 감사 4회 전부 NO-GO를 받고 정책 판정 트랙에서 계측·축 검증 트랙으로 내려앉았다(1.36 GPU-hr 집행, 새 성능 판정 0건). 그 과정에서 기전 하나가 코드 독해가 아니라 관측으로 확인됐다: --chunked-prefill-size가 prefill 예산과 piecewise CUDA graph 캡처 범위를 동시에 결정하며, cps −1에서 캡처 목록 길이가 0이다(job 900053). ⚠️ 스코프 = Zamba2-2.7B · 이 트리 · arm당 부팅 n = 1 ⇒ 정본 pdmux arm(전부 cps −1)으로의 파급은 미검증 관측일 뿐 판정이 아니다.

agnostic PD-mux — 채택된 유일한 구조

채택 · 운영 기본값
--enable-pdmux · manual_divisions: [[74,34,0]]

구조

green context로 108 SM을 정적 분할한다. layer도 phase도 모르는 policy-agnostic 고정 split이다 — 정책이 없다는 것이 이 구조의 내용이다.

측정

운영점(cudagraph-ON, n=5 paired) 정본 goodput 술어에서 fused를 2모델 전부 이긴다. 통계 정정 후 인용 가능한 정량치는 세 점: Zamba2 rate2 +40.5 % · rate3 +185.8 % · Granite rate4 +27.0 %.

이득은 꼬리에, 비용은 중앙에 있다 — 정상상태 per-token decode가 5–45 % 느려진다.

판정

실무 기본값. 검증된 profile이 없으면 agnostic, 있으면 peak decode 부하 기준 decode-heavy static 고정.

"SM 분할 자체가 원인"은 NOT-YET-SUPPORTED. --enable-pdmux가 --chunked-prefill-size -1·--disable-overlap-schedule을 assert로 강제하는 3-플래그 묶음 처치다. 후속 게이트가 두 aux 플래그를 원인에서 배제해 귀속 상한을 "pdmux 서브시스템 전체"까지 좁혔을 뿐이다. 운영점 대조는 2모델만 — "4모델 전부"는 더 이상 쓸 수 없다.

layer-type 인식 · coordinated per-type

全형태 死
manual_divisions: [[92,16,0],[34,74,0]] · sm_group_num: 4

구조

Hybrid 모델의 attention 레이어와 SSM(Mamba2) 레이어에 서로 다른 split을 준다. 이 프로젝트의 원래 논문 가설이었다.

측정

coordinated per-type 구현이 TPOT 42 → 124 ms. 최적화 후에도 ≈85 ms. 시뮬레이터가 약속한 per-layer 이득(1.37–2.02×)은 실엔진으로 전이되지 않았다.

판정

런타임 정책으로서 全형태 死. 死因은 결정 비용이 아니라 실행 파편화다 — offline 고정값으로 만들어도 attn↔mamba 경계마다 재분할이 필요해 그대로 죽는다.

살아남는 offline 역할은 whole-phase floor 하나뿐이다: step 내내 단일 파티션을 유지하되, 그 크기만 모델 구성으로 정한다.

2026-08-04 계측 결함 2종 감사로 마그니튜드는 강등됐다. 강등되지 않은 것은 판정 자체다 — 死 판정의 근거는 시뮬레이터가 아니라 서빙 직접 측정이다.

단일-worker 동적 제어

死 · HE0
CoarseGrainedController — SLO-aware · binding-first · feasibility gate

구조

런타임 신호(ITL p95, decode batch)를 보고 split을 옮긴다. 제어·데이터 평면은 fused와 동일하고, 바뀌는 것은 좌표뿐이다.

측정

관대 SLO(TTFT 3 s) goodput: d44 3.220 ± 0.013 > bind+GATE 3.132 ± 0.019 — 격차 5.4 σ, n ≥ 4.

tight SLO(chat 300/50 ms)로 컨트롤러를 실제 재튜닝해도 열위이고 오히려 격차가 벌어진다: rate 8 attainment d44 73.2 % ≫ bind+GATE 44.3 % (28.9 %p ≈ 10 σ).

판정

死. 死因은 switch 오버헤드가 아니라 positioning + 얽힘이다: 컨트롤러가 tight TTFT에 반응해 prefill 쪽으로 이동 → decode 굶김 → ITL↑ → batch 정체 → admission 차단 → TTFT 폭발.

feasibility 게이트의 정체는 동적 제어가 아니라 틀린 static에 조기 수렴하는 auto-tuner였다.

살아남은 동적의 값어치는 성능이 아니라 견고성이다 — 게이트가 트랩 붕괴를 1/4에서 0/5로 막았다. 그리고 달성된 동적의 열위(HE0)와 달성 가능한 천장은 다른 명제다.

R1 observer dual-worker

인과 귀속 철회
PDMUX_DUAL_WORKER=1 · 재현 전용

구조

기존 scheduler queue/batch의 alias와 logical arbiter를 추가했을 뿐, 동일한 event_loop_pdmux에서 실행됐다.

측정

dual arm에만 동기식 JSONL bookkeeping이 있었고, CUDA Graph가 꺼져 있었고, server seed가 달랐고, 각 arm은 한 번만 실행됐다.

판정

"4 improved / 0 worse / 3 mixed" 판정과 decode-heavy 성능 차이의 dual-worker 인과 귀속을 철회한다. 모든 scenario는 방향성 관측이며 통계·인과 미확정이다.

이 구조는 재현 목적으로만 남긴다. 아키텍처 분리 실험으로 인용하지 않는다.

R2 true dual-worker

미검증 · Claim D
PDMUX_TRUE_DUAL_WORKER=1 · thread-local role(ContextVar) 패치 필수

구조

두 long-lived host issue thread, role별 task queue, immutable ExecutionContext, safe-boundary resource lease. 읽기 전용 코드 리뷰가 확인한 실체는 control-plane dual-worker다.

running batch(max_running_requests)·KV/mamba pool·SM 파티션(SharedGpuArbiter의 단일 stream_index)은 전면 공유된다.

측정

없다. GPU correctness gate 통과 이력 0, results/r2_eval/ 미생성, architecture=true_dual telemetry 전무.

판정

미검증. Claim D는 "얽힘을 깬다"가 아니라 "control-plane coupling 감소"로 범위가 축소됐다. 별도 device pool과 mamba state transfer가 필요한 headroom에는 이 구현으로 도달할 수 없다 — 그 경로는 코드에 전무하다.

알려진 잠복 결함 1건: admission latch(r2_admission_limited)가 split batch가 None으로 배수되면 clear 경로 없이 True로 고착돼 prefill admission을 영구 차단할 수 있다. 사용자 결정으로 현재 수정 보류.

R2 정책층 — hybrid-informed decode floor

미검증 · Claim E (핵심 가설)
PDMUX_R2_POLICY=fixed|generic|hybrid · PDMUX_MODEL_PROFILE=<json>

구조

versioned HybridModelProfileV1과 보수적 floor 추정기가 offline에서 decode floor를 예측하고, 세 정책이 engine safe-boundary에 연결된다. layer composition은 런타임 스케줄링 경계로 쓰지 않는다 — layer-type 死 판정에서 유일하게 살아남은 사용처다.

측정

없다. Claim E의 existing evidence 칸은 문자 그대로 "없음"이다.

판정

이 프로젝트의 미검증 핵심 가설. 필요한 것은 architecture control · generic policy · static/oracle 대조 · profile 일반화(leave-one-workload/model-family-out).

구현 완료 ≠ 성능 주장 성립. 이 구분이 이 프로젝트에서 결론을 두 번 뒤집었다.

sticky partition — 계측 기판

correctness 통과 · 성능 판정 아님
PDMUX_STICKY_PARTITION

구조

엔진의 initialize_stream_groups가 마지막에 무분할 그룹을 항상 덧붙인다. 그 결과 이 기판에서는 "decode가 D SM에서 돌았다"와 "prefill이 동시 in-flight였다"가 같은 사건이 돼, 어떤 통계도 decode-SM 탄력도와 prefill 간섭을 분리하지 못했다. sticky는 라벨을 고정해 그 alias를 끊는다.

측정

correctness gate 통과 — CPU 회귀 40 tests + sticky 단위 12 + GPU smoke byte-identical 출력. 실현률 0.038/0.093 → 0.999/0.9994.

판정

구현·검증 완료. 성능 판정이 아니다 — 이 구조가 여는 것은 결론이 아니라 측정 가능성이다.

여전히 미해결: sticky 기판은 estimand 자체를 바꾼다(decode-busy 시 prefill이 벽시계 ~77 % 유휴 ⇒ 공동 예산 배분이 아니라 단일-테넌트 decode 측정에 가깝다). 하드웨어 SM 프로브(S3)는 미실행이다.

disaggregation — 별도 device pool

미구현
state-transfer 경로 전무 · mamba conv/ssm state migration 스캐폴딩조차 없음

구조

prefill과 decode를 다른 디바이스 풀에 두고 hybrid의 mamba/SSM state를 옮긴다. 코드에 존재하지 않는다.

측정

goodput을 TTFT-pass ⊗ ITL-pass로 분해하면 두 도너의 SM 합이 108을 넘는다. 그 초과분이 곧 단일 GPU가 지불하는 coupling tax다.

판정

미구현. 이 플레이트가 존재하는 이유는 동적 제어의 死가 곧 천장의 소멸은 아님을 자리로 보여주기 위해서다 — 두 명제는 다르다.

크기 인용 금지. 이 오라클의 "+16 %"는 n = 1~2 · overload-only로 강등됐고, ITL 도너가 완전 동률이라 "116"이라는 숫자 자체가 tie-break 의존이며, TTFT 임계를 ±10 % 훑으면 크기가 0.00 % ~ +19.75 %로 요동한다. 인용 가능한 것은 구조 대조뿐이다.

A. decode demand는 composition·context·load에 따라 변한다 부분 지지 prefill을 16 SM에 고정한 채 decode-SM만 16 → 92로 올리면 decode ITL p50이 2.36–2.91× 개선(4 arm, 모델-무관, ctx 1024). 단 이것은 decode 측 등량곡선이라 레버의 존재만 확립하며 정책 이득 근거가 아니다. 국소 탄력도가 구간별로 4× 다르므로 44 이상 구간에 이 비를 적용 금지.
