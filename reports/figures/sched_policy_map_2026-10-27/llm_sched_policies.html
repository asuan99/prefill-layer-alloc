LLM 요청 스케줄링 지도

LLM 서빙의 "스케줄링"은 정책 하나가 아니라, 요청이 GPU에 닿기까지 차례로 내려지는 다섯 가지 결정이다. 각 결정층마다 어떤 정책이 있고, 무엇을 얻고 무엇을 내주는지, 실제로 어떤 노브로 운용하는지 정리했다.

1–4는 요청이 지나가는 순서이고, 5는 GPU 메모리 상태가 큐로 되먹임되는 고리다. 정책들은 서로 맞물려 있어서 한 층만 바꾼 비교는 다른 층 설정에 따라 결론이 달라질 수 있다.

1라우팅·로드밸런싱

여러 인스턴스 중 어디로 보낼 것인가. 캐시 적중과 부하 균형이 서로 당긴다.

정책동작얻는 것내주는 것예
Round-robin / random상태를 보지 않고 분배단순, 오버헤드 0요청 길이 편차가 크면 불균형대부분 프록시 기본값
Least-load / power-of-two큐 길이·KV 사용률이 낮은 쪽 선택꼬리 지연 완화캐시 지역성 무시각종 LB
KV/prefix-aware같은 prefix를 캐시가 있는 인스턴스로prefill 연산 절감, TTFT 감소인기 prefix로 핫스팟 발생Preble, SGLang router, llm-d, Dynamo KV router
Dynamic rescheduling배치 뒤에도 실행 중 요청을 옮김부하·단편화 해소KV 이동 비용Llumnix
Program/agent 단위LLM 호출 묶음(워크플로) 전체로 우선순위·배치 결정end-to-end 지연 개선호출 간 의존 정보 필요Parrot, Autellix

2큐 순서

대기 중인 요청 가운데 누구를 다음 iteration에 넣을 것인가. 출력 길이를 미리 모른다는 점이 이 층의 근본 난제다.

정책동작얻는 것내주는 것예
FCFS도착 순서대로단순, 기아 없음, 예측 가능긴 요청의 head-of-line blockingvLLM 기본, SGLang fcfs
Priority요청에 붙은 우선순위 순tier 분리(유료/무료 등)저우선 기아 → aging 필요vLLM --scheduling-policy priority, SGLang priority
SJF / SRPT예측 출력 길이가 짧은 것부터평균 지연 크게 감소예측기 유지, 오차, 긴 요청 기아S³, Learning-to-Rank
MLFQ (skip-join)생성이 길어질수록 하위 큐로 강등예측 없이 SRPT 근사잦은 선점 → KV swap 비용FastServe
Fairness (토큰 기반)테넌트별 처리 토큰이 적은 쪽 우선다중 테넌트 공정성처리량 소폭 손실VTC
SLO / deadline-aware마감 여유(slack)가 작은 순, 못 지킬 요청은 뒤로SLO goodput 최적화SLO 추정 오차, 경계에서 진동EDF 변형, Andes
Cache/prefix-aware캐시된 prefix를 많이 공유하는 요청부터prefill 절감, 처리량 증가공유 없는 요청 기아SGLang lpm, dfs-weight

운용 실서비스 기본값은 여전히 FCFS가 대세다. SJF·priority 계열을 켤 때는 aging이나 최대 대기 시간 상한을 거의 항상 함께 둔다.

3배칭

언제, 얼마나 묶어서 한 번의 forward로 돌릴 것인가.

방식동작얻는 것내주는 것예
Static batching배치 전체가 끝나야 다음 배치구현 단순짧은 요청이 긴 요청을 기다림초기 서빙 시스템
Continuous (iteration-level)매 step 끝난 요청을 빼고 새 요청 투입GPU 활용 극대화prefill이 들어오면 decode가 멈춤Orca → 현재 모든 엔진 기본
Chunked prefill긴 prefill을 토큰 예산 단위로 잘라 decode와 같은 iteration에 섞음decode stall 제거, ITL 꼬리 안정긴 prompt의 TTFT 증가Sarathi-Serve, vLLM v1 기본

노브 iteration 토큰 예산 max_num_batched_tokens / chunk size, 동시 시퀀스 상한 max_num_seqs · max_running_requests, SGLang schedule_conservativeness.

chunk를 크게 잡으면 TTFT가 좋아지고 ITL이 나빠진다. 작게 잡으면 반대다. SLO에 맞춰 튜닝하는 값이다.

4Prefill / Decode 배치

compute-bound인 prefill과 memory-bound인 decode를 같은 자원 위에서 어떻게 공존시킬 것인가.

방식동작얻는 것내주는 것예
Prefill 우선새 요청이 오면 prefill부터TTFT 좋음decode가 멈춰 ITL이 튐vLLM v0 기본
Decode 우선 + 잔여 예산running decode를 먼저 채우고 남는 토큰을 prefill chunk에ITL 안정고부하에서 TTFT 증가vLLM v1, Sarathi-Serve
PD disaggregationprefill·decode를 다른 GPU/인스턴스에서 실행, KV 전송phase 간 간섭 제거, 각자 최적 병렬화KV 전송 비용, P:D 비율 고정 문제DistServe, Splitwise, Mooncake, TetriInfer
PD multiplexing한 GPU 안에서 SM을 나눠 두 phase를 동시 실행(green context 등)간섭·전송 비용을 함께 줄임분할 비율 선택이 곧 정책, 동적 전환 위험Bullet, MuxWise, NanoFlow(연산 단위)

우리 측정 (A100 80GB 1장, SGLang + green-context, hybrid attention+SSM 모델)

단일 GPU에서 SLO-aware, binding-first, gate 같은 동적 SM 분할 제어는 가장 좋은 decode-heavy 정적 분할을 넘지 못했다. 원인은 전환 비용이 아니라 위치 선정과 얽힘(entanglement)이었다. decode가 굶으면 ITL이 오르고, 배치가 정체되고, admission이 막혀 TTFT가 폭발한다. 이 기판에서의 실무 기본값은 peak decode 부하에 맞춘 decode-heavy 정적 분할이다. 다른 GPU 세대나 다중 GPU로는 그대로 옮겨지지 않는다.

5메모리 압박과 선점

KV cache가 모자랄 때 누구를, 어떻게 밀어낼 것인가. 선점 횟수는 꼬리 지연의 선행 지표다.

방식동작얻는 것내주는 것예
Recompute 선점KV를 버리고 나중에 prefill부터 다시추가 메모리 불필요연산 낭비 (짧은 요청에 유리)vLLM 기본
Swap 선점KV를 CPU 메모리로 내렸다 올림재계산 없음 (긴 요청에 유리)PCIe 대역폭 소모vLLM, FastServe
Live migration실행 중 요청의 KV를 다른 인스턴스로부하 균형, 단편화 해소네트워크·동기화 비용Llumnix
Admission controlSLO를 못 지킬 요청은 처음부터 거부받은 요청의 goodput 보호처리량 포기, 거부율 관리 필요Mooncake 조기 거부
보수적 KV 예약새 요청이 끝까지 쓸 KV를 추정해 미리 확보선점 폭풍 방지너무 보수적이면 배치가 작아짐SGLang new_token_ratio 계열

동작 시나리오

대표 기법을 같은 요청 묶음에 적용했을 때 시간축에서 무엇이 달라지는지 나란히 비교한다. 시간은 decode 1스텝을 1칸으로 단순화한 개념도이고, 측정값이 아니다.

워크로드별로 먼저 볼 정책

워크로드 성질을 고르면 위 표에서 먼저 검토할 행이 강조된다.

정책을 비교할 때

  • 지표: throughput보다 SLO goodput, 즉 TTFT와 요청 내부 ITL p95를 동시에 만족한 요청의 비율을 본다. TTFT·ITL은 p50/p95/p99를 함께 보고한다.
  • 부하 trace: 일정한 부하에서만 비교하면 동적 정책의 이득과 손실이 모두 가려진다. 부하가 바뀌는 trace(예: rate 3↔12)로 여러 라운드 비교한다.
  • metric cliff: goodput은 TTFT가 SLO 근처일 때 급변하는 지시함수다. 먼저 용량을 재고, 경계에서 떨어진 운영점에서 측정한다.
  • 분산 먼저: 베이스라인 반복 측정의 분산을 먼저 잰다. 반복 수가 부족하거나 몇 % 이내 차이라면 정책 우열을 말하지 않는다.
  • 시뮬레이터 이득은 가설일 뿐: 시뮬레이터나 마이크로벤치의 이득이 실엔진에서 사라지는 일이 흔하다. 정책 주장은 실제 서빙으로 확인한다.
  • SLO를 바꾸면 다시 튜닝: 다른 SLO에서 평가할 때 기존 컨트롤러를 새 기준으로 재채점하지 말고, 그 SLO로 다시 튜닝해 직접 측정한다.
