Is decode latency actually bound by SM count?

Stage 0 swept decode SM and prefill SM together (partition [108−D, D]), so its falling ITL(D) curve was judged a prefill-contention artifact, and the one clean contrast said decode is SM-insensitive. Pinning prefill at 16 SM and sweeping decode alone was meant to close that. It didn't: the flat curve failed to appear — and the slope shows up in the negative control too, which is either a surviving confound or evidence the control was never valid on this axis.

Act 1

The coupled sweep

Raising decode SM lowers prefill SM by construction, so the curve mixes two causes. Two controls show it is not measuring decode-SM binding.

Per-token latency vs decode SM — prefill co-swept

Evidence 1 — the no-split anchor

D108 (108 SM, zero prefill contention) is as slow as D16 to within 0.5% in all 9 cells, and slower than D92. More decode SM ≠ faster: the curve is non-monotone in SM, so it cannot be measuring decode-SM binding.

Evidence 2 — the pure-Mamba control

M (SSM-only, O(1) recurrent decode — no KV scan) was taken to be immune to decode-SM binding, yet reproduces the full 2.46× curve, same shape as H. Act 2 revisits whether that immunity premise holds.

Mechanism — 5× wall collapse

The one fast point, D92, is where prefill is starved to 16 SM. Wall-time inflates 5.0–5.4× uniformly: the run serializes, it doesn't accelerate. Lower ITL is de-batching, not speed.

The signal Act 2 tests

The only de-confounded contrast, D16 vs D108, = 1.00 ± 0.01 across 3 arms × 3 ctx. Caveat since recorded: these are not two zero-contention points — D16 runs keepalive prefill, D108 runs none. It survives as an upper bound, not an equality of like with like.

Act 2

Prefill pinned at 16 SM, decode swept alone

Green-context honours a partition pair summing below 108 (probe 864669), so prefill can be held fixed while only decode moves — the remainder simply idles. Run 865098, n=4, all PIN_CHECK pass.

The de-confounded sweep, and what still contaminates it

The prediction failed

Pre-registered before the run: ITL flat across D (<5% spread) in all three arms. Observed D16/D92 = 3.05× (M), 8.59× (H), 2.07× (T). H0 is dead.

But H1 is not adopted

Decode batch size fell with D (H: 8.44 → 3.28). The closed loop fixed requests in flight, not the decode batch — prefill at 16 SM became the bottleneck, so faster decode drained its phase sooner. The realized-occupancy instrument caught this; asserting fixed occupancy would have let it pass as clean.

Slope survives matched batch

Stratifying engine telemetry so only equal batch sizes are compared leaves ≈2–2.7× in every arm. Some bins invert (M b3 0.95×, T b4 0.87×) and the EWMA-to-batch pairing is approximate — suggestive, not settled.

The crux — why does the control slope?

(a) A confound remains, and everything above is void. (b) The premise is wrong: O(1) is in context length, not in SM count — a Mamba2 decode step still does real matmul work that 16 vs 92 SMs changes.

Under (b), M was never a valid control here and the slope is real — which would make Stage 0's null the artifact.
