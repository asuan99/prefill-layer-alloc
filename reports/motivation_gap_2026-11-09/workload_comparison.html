워크로드 분포 대조

프로젝트 워크로드와 기존 연구의 입력·출력 길이, 도착 과정, 요청률을 나란히 놓고 motivation 측정 설계를 검토했다. 결론은 세 가지다. 짧은 챗과 장문 요약은 문헌과 맞지만 그 사이 길이대가 비어 있고, 장문 요약의 출력 조건이 캠페인마다 달라 고정해야 하며, 요청률은 고정값이 아니라 워크로드마다 사전 측정으로 정해야 한다.

2026-11-09. GPU 실행과 새 판정은 없다. 프로젝트 값은 저장소 원자료에서 계산했고, 문헌 값은 논문 표·본문·그림에서 옮겼다. 그림에서 읽은 값은 근사다. 권고는 측정 사전등록의 감사를 받기 전 초안이다.

입력 길이

이 프로젝트기존 연구점 = 중앙값 또는 평균, 선 = 보고된 범위

"ShareGPT"가 프로젝트 안에서도 두 분포다

ShareGPT V3의 대화 92,886건 중 34,087건(37%)은 모델 발화로 시작한다. SGLang 샘플러는 화자와 무관하게 첫 두 턴을 쓰므로 이 경우 모델 답변이 프롬프트가 된다. 현재 하네스는 사람→모델 순서만 남겨 입력 중앙값이 33토큰이고, SGLang 규칙을 재현한 2026-09 센서스는 151토큰이다. 문자 수로 보면 사람 시작 대화의 중앙값은 141자, 나머지는 1,809자다.

그러므로 "SGLang 벤치마크와 같은 ShareGPT"라고 쓰면 틀린다. 평균 230은 MuxWise(226), NanoFlow(246)와 같은 대역이다.

MuxWise가 쓴 LooGLE와의 대조

장의존 QA의 정답 길이는 평균 15.1, 최대 326으로 MuxWise 표의 출력(평균 15, 최대 326)과 일치한다. 그래서 MuxWise는 장의존 QA의 정답 길이를 출력으로 쓴 것으로 보인다(추정). 입력 평균도 33k로 가깝다. 다만 MuxWise의 최소 입력 3,380은 재현되지 않는다. 전체 데이터에 12,361토큰보다 짧은 입력이 없고, 논문은 절단이나 표집 방식을 밝히지 않았다.

  • 메모리 영역: 모든 요청이 메모리 교차점(약 8.8k)보다 길다. arXiv 요약 16k의 중앙값 6.5k는 그 아래이므로, LooGLE는 지금 비어 있는 영역을 채운다.
  • decode가 거의 없다: 장의존 QA 출력 중앙값은 7토큰이다. decode SM 분할을 시험할 대상이 적다. 프로젝트의 장문 계획 문서도 단독 사용을 부적합으로 적었다.
  • ITL 조건이 성립하지 않는다: 출력이 1토큰이면 ITL이 없고, 몇 토큰이면 p95가 사실상 최댓값이다. 단독 셀은 TTFT(입력 토큰당 정규화) 중심으로 평가해야 하며, 게이트 4의 ITL 항을 어떻게 다룰지 사전등록에서 정해야 한다.
  • 혼합이 PD-mux에 맞는 시나리오다: MuxWise도 ShareGPT:LooGLE 50:50, 0.5 req/s로 긴 prefill 중 짧은 요청의 진행을 시험했다. 짧은 챗이 decode를 공급하고 LooGLE가 긴 prefill을 공급한다.
  • 서버 설정이 달라진다: 현재 --context-length 20480이면 요청의 72%가 잘린다. context와 --max-prefill-tokens를 약 96k로 올린 별도 boot가 필요하고, chunk 없는 prefill 상한 약 94.8k를 넘는 0.4%는 제외한다. 메모리 비율은 결정 13의 장문 조건과 묶인다.
  • 문서 공유: 6,448문항이 916문서를 공유한다. radix OFF에서는 영향이 없지만, prefix cache를 켜면 결과가 달라진다.
  • 요청률은 미정이다: 무경합 prefill 측정식을 16k 밖으로 외삽하면 32k 입력 한 건에 약 3.6초다. 0.3 req/s 아래가 축이 될 것으로 보이지만 16k 초과 선형성은 미측정이다.

혼합 분포

우려하신 대로 짧은 챗과 LooGLE을 섞으면 분포에 문제가 생긴다. 넓은 것보다 두 봉으로 갈라지는 것이 핵심이다. ShareGPT의 최대 입력은 3,897토큰이고 LooGLE 장의존 QA의 최소는 13,459토큰이라, 그 사이에 요청이 하나도 없다. Nano의 메모리 교차점 8.8k도 이 빈 구간 안에 있어서, 혼합은 경계 영역을 시험하지 못한다.

결정(2026-11-09): 주 분포가 아니라 간섭 시험으로 쓴다

주 측정은 단일 분포 셀(ShareGPT, openchat, arXiv 요약)로 하고, LooGLE은 짧은 요청의 rate를 고정한 채 LooGLE 5%를 얹는 짝 비교 셀로 넣는다. 보는 값은 LooGLE이 있을 때와 없을 때 짧은 요청의 TTFT·ITL 악화폭, 그리고 LooGLE 자체의 입력 길이당 TTFT다. 결과는 요청 부류별로만 보고하고 합산 attainment는 주 지표로 쓰지 않는다. 경계 영역까지 덮는 연속형 분포가 필요하면 openchat 80 · arXiv 15 · LooGLE 5가 후보다(CV 1.7).

rate와 건수는 prefill 무경합 측정식(9 ms + 0.111 ms/토큰)을 16k 밖으로 외삽해 prefill 사용률 0.7로 계산했다. decode 병목은 넣지 않아 2% 이하의 높은 rate는 실제로 도달하지 못할 수 있다. Mooncake 실측 p99/p50은 12.4로, 5% 혼합의 약 1,175보다 훨씬 좁다.

모델별 메모리 교차점

교차점은 모델 config만으로 실행 전에 계산된다. 정본 수식(analytic-v1)의 s = n_M·[n_h·p·N·β_s + (n_h·p + 2GN)(K−1)·β]는 요청당 고정 Mamba 상태, k = n_A·2·n_kv·d_h·β는 토큰당 KV이고, 상주 메모리가 같아지는 길이가 L* = s/k, decode 트래픽의 두 항이 같아지는 문맥이 c* = 2s/k다.

  • 워크로드 선택은 대부분 모델과 무관하다: 짧은 챗은 어느 모델에서도 L*에 닿지 않고, LooGLE는 47B를 뺀 모든 모델에서 L*를 넘는다. arXiv 요약은 L*에 걸쳐 있어 모델에 따라 26–86%가 넘는다.
  • c*는 더 멀다: Nano의 c* 17.5k는 arXiv 요약 16k 필터 위에 있다. decode에서 KV 항이 상태 항을 넘는 구간은 LooGLE·Mooncake 쪽에서만 나온다.
  • 이 식이 말하지 않는 것: 출력 길이로 늘어나는 KV, 동시 실행 수, cudagraph 패딩, 실제 성능 차이는 담지 않는다. 교차점을 넘는다고 hybrid의 이득이 생긴다는 뜻이 아니다.
  • 확인하지 못한 것: Nano 외 모델의 부팅 배너 대조. Falcon-H1과 Granite의 s, k는 SGLang config 코드와 공개 config로 계산했다. Jamba Mini와 Zamba2-7B는 config 접근이 막혀 있었고, Zamba 계열은 프로젝트 배제 결정(결정 46)에 따라 대상에서 뺐다.

요청률 축

요청률에 공용 고정값은 없다. 고정되는 것은 데이터셋, 도착 과정, 달성률 문턱이고, 축은 각 논문이 자기 조건에서 용량이 꺾이는 곳을 감싸도록 잡는다.

확인하지 못한 것

  • 대부분 논문의 부하점당 run 길이와 요청 수(논문에 적혀 있지 않음).

  • ServeGen 언어 워크로드 평균, Flex 보충자료.
  • LooGLE 각 과제를 실제로 서빙했을 때의 요청률과 메모리 동시성. Nano에서 96k 입력 동시 처리 수는 측정된 적이 없다.
