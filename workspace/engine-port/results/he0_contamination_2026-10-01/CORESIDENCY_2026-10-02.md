## 과제 A — 재구성 self-test 보강 (`he0_selftest_v2.py`)

**합성 엔진은 재구성 규칙과 다른 생성 규칙을 쓴다.** 서버 시계 기준으로 반복(iteration) 단위 루프를 돈다. 종료한 요청은 다음
반복 경계에서 빠지고, prefill을 마친 요청은 그 다음 경계에서 합류한다. 로그에 남는 `#running-req`는 **서버** 측 running 집합이다.
재구성은 이와 달리 **클라이언트 수신 시각** [첫 토큰, 마지막 토큰)으로 running 수를 센다.

규모는 실데이터에 맞췄다.
- prefill in-flight: 중앙값 62–113 ms.
- 반복 하나가 도는 시간: 0.0095 + 0.00022·bs. 실측 decode-only ITL은 bs 5에서 10.6 ms, bs 45에서 19.4 ms다.
- 입장 반복에 45 ms stall이 붙고, in-flight 동안 반복이 f배 느려진다. f는 실제 토큰 타임라인 4라운드(856890·859008)에서 가져왔다.
- 클라이언트 수신 지연: 12 ms + 0.4 ms·bs + AR 잡음, 약 12–35 ms.
- 송신 지연은 0.4 ms/요청씩 drift한다.
- 입력·출력 길이는 실데이터 856890 round 0의 것을 썼다.

시나리오는 phase{LO,HI} × D{44,16} × 지연{0, 실규모} × 송신정지{없음, 3 s} = 16개다.
**T1** = |CO_pt − 진실| ≤ 0.02(v1과 같은 허용 폭), **T2** = 배치별 in-flight 길이 오차 중앙값 ≤ ±15 ms. 둘 다 사전등록했다.

**무변이 대조: 16 시나리오 중 5개만 PASS**(LO 2, HI 3). 실패 11개는 전부 재구성이 **위로** 치우친 경우다.

| 영역 | pt − 진실(동거 시간비) |
|---|---|
| LO, 지연 0 | +1.4 … +2.9 pp |
| LO, 실규모 지연 | **+4.0 … +6.1 pp** |
| HI D44 | +0.7 … +3.3 pp |
| HI D16 | +1.4 … +5.6 pp |

이 상향 편향은 재구성 규약 자체의 성질이다. 기전은 두 가지다. LO에서는 s_pt가 도착 시점에 붙는데 e_k는 클라이언트 지연만큼 늦다.
HI D16에서는 prefill이 짧아 재구성의 1-반복 정렬 오차가 상대적으로 커진다.

**변이 판정** (변이는 `reconstruct_round` 소스를 정확히 한 군데 치환해 만들었다. 무치환 사본이 원본과 비트 단위로 같은지 확인했다.
판정은 대조가 PASS한 5 시나리오에서만 했다.)

| 변이 | 판정 | 비고 |
|---|---|---|
| intersect→union, 도착 seed, 시계 +1 s(v1에서 이어받음) | KILLED 5/5 | |
| **(b) `s_pt := 최조기`** | **PARTIAL — HI 3/3 KILLED, LO 0/2 SURVIVED** | HI에서는 +20 … +34 pp로 확실히 잡힌다. LO에서는 pt와 최조기가 사실상 같은 점이다(실데이터 LO 20.4 vs 20.5%, 합성 LO 차 ≤0.3 pp). **LO에서는 등가 변이라 원리적으로 못 잡는다**. 검사 설계의 한계로 그대로 둔다. |
| **(c) `e + 30 ms`** | **KILLED 5/5** | +5.6 … +9.2 pp, 길이 오차 +23 … +34 ms |

합성 세계에서 각 규약이 진실과 어떻게 어긋나는지 보면(기술 통계, 판정 아님): HI 진실은 [+1 iter, pt] 사이에 있다.
최조기는 +14 … +36 pp로 크게 과대하고(cap 48 포화에서 slot 대기를 in-flight로 센다), 최만기는 −26 … −40 pp로 크게 과소하다(창 시간비 기준).
**이 대응 관계는 합성 엔진의 입장 규칙(slot이 비면 즉시 입장)이 만든 것이다.** 실엔진이 같은 규칙이라는 증거는 아니다.

## 과제 B — 동거 구간 독립 추정량 (`he0_coresidency_indep.py`)

추정 원리: split prefill이 in-flight인 동안 decode 반복은 느려진다. 따라서 느린 decode 토큰이 덮는 시간으로 in-flight를 직접
추정한다. running 수 정합, s_pt, 시작 bracket, T_log는 **쓰지 않는다**.

**사전등록(파일 상단).** 실데이터에서 어떤 추정량도 실행하기 전에 고정했다.
- k 격자 {1.25, 1.5, 2, 3}.
- 기준선 = 이웃 ±1.5 s 안 ITL의 20번째 백분위.
- 아티팩트 규칙: A1 ITL > 0.5 s, A2 수신 몰림(bunching). 걸린 구간 ±0.5 s를 X로 두고 분자와 분모에서 모두 뺀다.
- 합성 자격: 해당 영역의 비-stress 시나리오 전부에서 |오차| ≤ 0.03, 그리고 수신 정지 구간의 ≥90%가 X에 덮일 것.
- k* = HI D44와 HI D16 둘 다에서 자격을 얻는 가장 작은 k.
- 판정: REAL / NOT-REAL / INCONCLUSIVE 규칙은 파일 상단에 있다.

**공개(사전등록 전에 본 것).** 합성 엔진의 모양을 잡으려고 실제 토큰 타임라인 4라운드를 먼저 봤다. 그중 한 HI 구간은 느린 토큰이
최조기 쪽과 맞아 보였다. 이 사전 관찰이 편향 요인일 수 있다.

### B-1. 합성 검증

**v1(사전등록, 반복 군집 기반): 탈락.** HI에서 자격을 얻는 k가 없다(최대 오차 0.15–0.33).
- 원인: 재구성의 요청별 송신 drift 적합 오차가 요청 번호에 비례해 쌓인다. 그래서 같은 반복의 토큰들이 수십 ms 범위로 퍼진다.
  합성 HI에서 군집 spread p95가 17–125 ms였다.
- 그 결과 A2(몰림) 규칙이 오발화해 창의 30–80%가 X로 빠졌다.
- **실데이터 HI도 같은 현상을 보였다**(spread p95 8–100 ms, 라운드당 몰림 0–185개). 실패 진단을 위해 이 개수만 봤다.

⇒ **새로 확인된 한계**: HI에서 재구성의 요청 간 상대 정렬은 수십 ms 수준이다. 100 ms 규모의 in-flight 구간 배치를 이 정렬로
다투는 것은 모형 의존이다(감사 #11의 ~0.3–1 s 한계보다는 낫지만, 100 ms에 비해 무시할 수준은 아니다).

**수정 1(실데이터 실행 전에 기록) → v2(요청별 추정량).** 분자에는 각 요청 자신의 ITL 열만 쓰므로 요청 간 정렬이 필요 없다.
추정량은 RTW(요청-시간 가중 동거 비율 = 동거 중 decode ITL 시간 ÷ 전체 decode ITL 시간)로 바꿨다. 배치별 시작점 시험은
정렬이 필요해서 폐기했다. **v2도 탈락했다(k* = None).**

- **LO D44**: in-flight 중 decode 감속이 약 1.05배라서 원리적으로 검출할 수 없다. 실데이터 LO d44도 stall 뒤의 반복은 11 ms로 거의 정상이다.

## 과제 C — `he0_followup.py` self-test 보강 + 반박된 수치 재계산 (`he0_followup_selftest_v2.py`)

시험 대상은 모듈 자신이다. 변이는 모듈 전체 소스를 정확히 한 번 치환해 새 namespace에서 실행했다. 그래야 `c4_run`처럼
변이된 함수를 호출하는 쪽도 변이본을 쓴다. 무치환 재실행본이 import본과 출력이 같은지 확인했다(True).

**합성 정지 주입.** 과제 A의 엔진에 기본값 꺼짐 옵션을 추가했다(과제 A·B 출력은 바이트 동일, sha256 확인). 옵션은 서버 스케줄러
정지(HTTP 동반 무음 / HTTP 생존)와 합성 서버 로그(Decode 40반복마다, POST, Prefill; 1초 타임스탬프)다. 요청에 있던
`he0_realized._synth`는 서버 로그를 만들지 않아 정지 분류를 시험할 수 없어서 대신 이 엔진을 썼다. 정지는 첫 송신 후 5.3 s,
길이 3.5 s, HI D44다.

| 시험 단위 | 무변이 대조 |
|---|---|
| T-S no_stall / client_send_only (사건 없어야 함) | PASS / PASS |
| T-S server_wide → SERVER_WIDE | PASS (Decode 줄 0/3.5, HTTP 수신 지연 3.9 s) |
| T-S server_sched → SERVER_SCHEDULER | PASS (Decode 줄 0, POST 31줄 생존) |
| **T-S client_recv → CLIENT_RECEIVE** | **FAIL: CLIENT로 분류** |
| T-S client_loop(송신+수신 정지) → CLIENT | PASS |
| T-C1 `c1()` 실제 호출 기지값 혼합(R/SD = 0, −3, +3; pooled SD; exclude) | PASS (7 술어 × 2 배치 전부 1e-9 이내) |
| T-OCC `running_and_queue` 기지값 | PASS |
| T-C4 `c4_run` vs 합성 서버 진실 occupancy ≥46 | PASS (재구성 0.512 vs 진실 0.509) |
| T-ZT `zero_transition_contrast` 기지값 | PASS |
| T-IPA `index_paired_attribution` 기지값 | PASS |
| (사후 추가) 송신 종료 후 수신 정지 → CLIENT_RECEIVE | PASS |

**client_recv 실패 원인.** 송신이 진행 중인 구간에 수신 정지가 겹쳤다. 그러면 새 요청들의 첫 토큰 수신이 늦어지고, 재구성의
송신 오프셋 적합이 이것을 송신 지연 계단으로 해석한다. 이 사례에서 가짜 계단은 2.91 s였다. 그래서 하위 라벨이 CLIENT
(송신 계단)로 바뀐다.

이 시험이 보여 주는 것:
- **서버측과 클라이언트측의 최상위 구분은 5/5 맞다.** 856964 = SERVER_WIDE 판정의 근거가 이 구분이다.
- **CLIENT와 CLIENT_RECEIVE의 하위 라벨은 송신 구간과 겹치는 정지에서 믿을 수 없다.**
- client_recv에서 Decode 줄 연속성은 2/3.78 = 0.53으로 0.5 문턱 바로 위였다. 내부 3초짜리 짧은 정지에서는 서버/클라이언트
  분기도 경계적이다.
- 실데이터의 해당 사건(856892 HI2: 송신 종료 후, 859006 HI2: CLIENT_RECEIVE 13.85 s)의 하위 라벨은 이 단서와 함께 읽어야 한다.
