# M3 축소 재실행 범위 선택지 (2026-10-19, 미커밋 · 계획 문서 · 판정 아님)

> **지위**: 로컬 CPU 계산과 문서만 했다. 봉인 파일·`results/multigpu/`는 건드리지 않았고 GPU·VESSL 작업도 없다. **이 문서의 수치는 모두 시간 모형 추정 [유도]이며 측정값이 아니다.**
> J1 결과값(λ\*·G)은 **시간 모형 입력(λ/prior 비, 반올림)으로만** 썼다. 감사 전 값이므로 결과로 인용하지 않는다.

## 0. 요약

- **rev12 전체(S0)는 J1에서 보인 확장 발화(B·X)를 넣으면 J2·J4·J8이 20.3–21.5 h [유도]가 걸린다.** 등록 캡 16 h를 넘고, 관측된 9.5 h 외부 정지보다는 훨씬 길다. 봉인 예산 190 GPU-h는 "확장 없음, λ = prior" 가정에서 나온 값이다. J1 보정 모형으로는 예약 297–315 GPU-h [유도]가 된다(캡에서 잘리면 252 GPU-h).
- **권고 = S2f**: TP만 다시 잰다. arm은 fused·fused_sym·agnostic 3개, shape는 A·B, N은 {2, 4, 8}이고 N마다 Job 1개를 두며 각 Job에 자기 N=1 앵커를 붙인다. **J1과 rev12 J_N의 DP 결과는 재사용하고 J1은 다시 돌리지 않는다.** 비용 [유도]은 예약 70.9 GPU-h, 사용 60.9 GPU-h(86%), 최장 5.18 h다(M0–M1 범위 3.98–5.55 h, 봉인 forecast 최악 7.67 h). **전제**: fetch 결과 세 J_N 모두 DP의 fused_sym·agnostic boot1·ext·boot2가 끝나 있어야 한다. 이 확인은 LABELS 값이 아니라 boot rc와 파일 완결성만 보고 한다. 아니면 그 N에 S9f를 더한다.
- S2f를 고르는 이유: S2(2-arm)보다 17.6 GPU-h 비싸다. 대신 **x_lo 유도 규칙(LO rung = fused HI 중앙값 × 0.6)을 바꾸지 않는다.** 그래서 J1·rev12 DP 자료와 LO 정의가 같고, G_def 추세도 유지된다. 2-arm 안은 이 규칙을 바꿔야 하고, TP 추세 한 줄 안에 LO 정의가 다른 점이 섞인다.

- **사본**: `scratchpad/m3scope/mg_const.py`·`mg_plan.py`는 봉인 바이트와 같다(sha256 `836fe4a1…`, `7519e6f6…`; 스크립트가 import 전에 단언한다). 범위 모형은 `scope.py`다. 봉인 함수 `cell_seconds`·`hi_rung`·`lo_rung`·`n_req_for`·`CALIBS`와 `EST_*` 상수를 그대로 쓰고, boot 목록만 범위 인자(arm, shape, config, seed 수, 앵커 shape, floor·xcheck, (config, shape)별 확장)로 다시 만든다. 교차검증 `patched.py`는 봉인 함수 `m3_budget`·`m3_plan_counts`·`m3_forecast_table`에 **상수만** 바꿔 넣은 것이다(`C.ARMS`, `C.SHAPES`, `C.ANCHOR_SHAPES`, TP-only 안은 `config_order`).

- **보정 3종**:
  - **M0** = 봉인 기본값(λ = prior, 확장 없음, audited). 봉인 dry-run과 같은 가정이다.

  - 참고 M2(TP λ × 0.7)는 TP 확장이 발화하지 않아 M1보다 짧았으므로 상한으로 쓰지 않는다(`scope_stdout.txt`).

## 4. 안별로 잃는 것과 1차 판정(P9·P10·P11)에 미치는 영향

1차 판정 문장은 G_sym에만 붙는다. G_def·G_d44sym은 보조 라벨이고 판정을 열거나 막지 않는다(rev11 §4-4). 따라서 보조 estimand를 버려도 **P9·P10·P11의 계산 대상은 그대로다.** 영향은 아래의 간접 경로로만 생긴다.

| 손실 | 해당 안 | 1차 판정에 미치는 경로 |
|---|---|---|
| **X shape** | S1–S9f 전부 | 이미 P9-a로 X 방향 라벨 전부 인용 불가(J1 N1 xcheck FAIL → G_sym(1, X) 미정의). U12에 따라 P10은 {A, B}와 {X}에 따로 적용되므로 X를 빼도 A·B의 P-DP·MGP-13·P11(b)는 바뀌지 않는다. 잃는 것은 X 앵커 Job 효과 기술치, X floor 경로 기술치, J_N TP의 16k xcheck(U7이 겨냥한 TP split-prefill 16k 경로 시험)다. 마지막 것은 정확성 증거라서 판정과 무관하게 공시 손실이다. |

## 5. 이미 실행된 자료와 섞어도 되는가

**바이트 사실**:
- J1 커밋은 `2106f421`, J2·J4·J8 커밋은 `e559c647`·`213df1b3`·`3167f742`다. `git diff --stat 2106f421 408bcd41 -- workspace/engine-port`의 결과는 `vessl_jobs.tsv` 4줄뿐이다(제출 장부). → **J1과 rev12 J_N은 규칙·하네스·측정 경로 바이트가 같다.**
- 축소안(rev13) Job은 적어도 `mg_const.py`(ARMS/SHAPES/ANCHOR_SHAPES/HARD_CAP/M3_CELLS_EXPECTED/PREREG_REV), `mg_plan.py`(X가 없을 때 xcheck 삽입, TP-only config 순서), `mg_label.py`(교차 Job·교차 rev 결합), `tests/`(560·20·24·14·70 단언)가 바뀐다. 2-arm이면 `mg_drive.py`의 x_lo도 바뀐다. `tests/`는 §19-6 (iii)의 게이트 경로이므로 **CPU preflight를 다시 해야 한다.**

**섞어도 되는 조건 (S2f 기준)**:
1. **같은 Job 원칙**은 유지된다. 각 config의 arm은 모두 한 Job 안에 있다(DP_N은 rev12 J_N, TP_N은 rev13 J_N). rev12 J_N에서 TP가 일부 돌았다면 그 TP 셀은 버린다. rev13 TP와 합치면 같은 config의 arm이 두 Job에 나뉘므로 원칙 위반이다.
2. **Job 효과 앵커**: rev13 TP Job마다 자기 N=1 앵커(fused_sym·agnostic, A HI 4 seed)를 J1 boot1과 대조한다(§15-3·P9-b 그대로). DP는 rev12 J_N 앵커로 이미 측정됐다(앵커는 DP보다 먼저 돈다). 따라서 J1은 두 계열 모두의 공통 기준으로 쓸 수 있다. B는 rev12처럼 A 앵커 기준이다.
3. **측정 경로 바이트 불변을 봉인 조건으로 둔다.** `mg_boot.py`·`mg_loadgen.py`·`mg_runner.sh`·`mg_proc_sampler.py`·`trace_loadgen.py`·`context_limit.py`, 엔진 digest `82a5fc5b…`, 이미지 digest, runner 인자(ctx 20480, max_prefill 16384 등)가 rev12와 바이트로 같아야 J1·DP와 섞을 수 있다. rev13 봉인 기록에 "rev12 대비 측정 경로 diff = 0" 목록을 적고, 하네스층 감사가 확인한다.
4. **x_lo 규칙을 바꾸지 않는다(3-arm).** 그래야 J1·rev12 DP·rev13 TP의 LO rung 정의가 같다. 2-arm(S2)이면 이 조건이 깨진다.
5. **외부 종료 Job의 DP 사용 규칙을 rev13에 등록한다.** rev12는 하드캡 절단(`TRUNCATED`)만 정의하고 외부 종료는 정의하지 않는다. 등록할 내용은 셋이다. (a) boot 기록 rc 0이고 셀 파일이 완결이며 fetch sha256이 통과한 boot만 쓴다. (b) 미완 셀은 `TRUNCATED`로 둔다. (c) LABELS는 봉인된 `mg_label.py`(같은 바이트)로 오프라인에서 다시 만든다. **주의(P11(b))**: DP 추세가 절단 때문에 `TREND_UNDEFINED`가 되면 TP 방향 라벨은 `TP_UNCONTROLLED_TRUNCATION`으로 인용 불가다. 따라서 DP boot2가 하나라도 미완이면 TP를 다시 재도 소용이 없다. 그 N은 S9f(DP 재측정)가 먼저다.
6. **공시 의무**:
   - (i) DP_N과 TP_N이 더 이상 같은 Job이 아니다. P-DP는 TP의 하네스·Job 건전성 대조 역할을 해 왔는데, 그 근거의 일부("같은 노드라 Job 효과를 공유")가 약해진다. MGP-13 형식 논리는 유지된다.
   - (ii) J1 boot1(floor+xcheck+A·B·X), rev13 앵커(floor+A), rev13 boot1(floor+A·B)은 boot 안 구성과 shape 순서가 다르다. rev12 앵커(A·X)에서도 이미 있던 종류의 차이지만 다시 적는다.
   - (iii) 측정일이 다르다(J1·DP 2026-10-18, TP는 그 뒤).

**J1이나 N=1 앵커를 다시 돌려야 하는가**: **J1은 다시 돌리지 않는다.** rev12 규칙상 G(1)은 1회차 값이다(MGP-10). 재측정한 G(1)은 드리프트 검사에만 쓸 수 있다. 1회차를 본 뒤 2회차를 기준으로 바꾸는 것은 자유 표면이다. 특히 **X를 살리려고 J1을 다시 돌려 xcheck 통과를 노리는 것은 "통과할 때까지 재시도"다** → 하지 않는다. N=1 앵커는 rev13 TP Job마다 새로 넣는다(Job 효과 검사에 필수다. 빼면 전 TP 점이 `JOB_EFFECT_UNTESTED`).
예외가 있다. 측정 경로 바이트 불변(조건 3)을 지킬 수 없으면 J1·DP와 섞을 수 없다. 그때는 S1f + J1rf(전부 새로, 예약 [유도] 128.1 + 8.7 GPU-h, M1a)가 필요하다. 이 경우 S1f J_N이 9.4–9.5 h라서 9.5 h 정지에 닿는다. 그래서 DP와 TP를 같은 N의 별도 Job 두 개(S9f + S2f)로 나누는 편이 낫다(합 141.8 GPU-h, 최장 5.18 h [유도]).

## 6. PREREG 개정(rev13)·감사·자유 표면

**개정은 필요하다.** arm 집합·shape 집합·config 집합·셀 수 상수·하드캡·교차 Job/교차 rev 결합·외부 종료 처리는 모두 등록 규칙이다. 순서는 rev12와 같다. 규칙층 감사(claims-auditor, 최대 2회) → 하네스 수정 → 하네스층 감사(최대 2회) → 재봉인 → CPU preflight(tests/ 경로 변경) → dry-run → 사용자 승인 → 제출. rev13에 넣을 최소 항목은 다음과 같다.
- 범위: TP_N(N = 2, 4, 8) × {fused, fused_sym, agnostic} × {A, B}, HI 4 / LO 2 seed, 앵커 A만(+floor), xcheck 없음(X가 없으므로)
- 재사용: J1(N1, A·B)과 rev12 J_N의 DP_N(A·B, 4 arm 자료 중 등록 estimand)
- 측정 경로 바이트 불변 목록, 외부 종료 처리(§5-5), 셀 수 상수, 새 하드캡(제안: J_N 8 h — M1 5.55 h, 봉인 forecast 최악 7.67 h를 덮고 9.5 h 정지보다 아래 [유도·제안])
- P10 그룹: {A, B}만, X 그룹 소멸. P11(b)는 교차 Job DP에 그대로 적용
- 금지 서술 추가: "TP와 DP가 같은 Job에서 쟀다", "d44의 N·mode 추세", "X의 N 추세", "TP16k 정확성"

**자유 표면 (데이터를 본 뒤의 축소)**:
1. **X 제외는 xcheck FAIL을 본 뒤의 결정이다.** 다만 그 FAIL의 결과(X 방향 라벨 전부 인용 불가)는 rev12 P9-a가 **미리 정해 둔 귀결**이다. X를 계속 재도 같은 규칙 아래에서는 인용할 수 없는 추정량만 늘어난다. 또 U12 그룹 분리 때문에 X를 빼도 A·B 판정은 유리하게도 불리하게도 바뀌지 않는다. 따라서 **1차 판정 방향으로 쏠리는 선택 표면은 없다** [판단]. 위험은 반대쪽에 있다. **정확성 발견을 묻는 것**이다. rev13과 결과 문서에 다음을 사실로 적어야 한다. "J1 N1 xcheck FAIL(`FIRST_16_MISMATCH` doc 2693, 16k 입력, fused_sym 대 agnostic)." 또 B(8k, `[1]*L` 합성)가 같은 split-prefill 장입력 경로 계열인데 이 FAIL이 B에 대해 무엇을 뜻하는지는 **미판정**이다. 이것을 rev13 규칙층 감사 질문으로 올린다. B의 정확성 근거는 M2g G1 범위(등록 prompt 64개, max_new 128)뿐이다.
2. **d44·fused 제외는 J1 LABELS(보조 라벨 값 포함)가 출력된 뒤의 결정이다.** 보조 estimand라 판정 영향은 없다. 그래도 "J1에서 본 값 때문에 뺐다"는 의심을 막으려면 제외 사유를 비용(셀 수·GPU-h)으로만 적어야 한다. S2f는 fused를 유지하므로 G_def는 남는다.
3. **DP 재사용 결정은 DP 값을 보기 전에 고정한다.** fetch 뒤 완결성 판정에는 `DRIVER_LOG.jsonl`의 boot rc·셀 파일 존재·sha256만 쓴다. rev13 봉인 전에는 DP LABELS(G 값)를 열지 않는다. 열었다면 그 사실을 공시한다.
4. **B 제외(S7)와 N=8 제외(S3·S4)**: B 제외는 J1 B 라벨 공개 뒤라서 선택 표면이 있다. N=8 제외는 TP 값이 아직 없으므로 데이터 의존은 아니지만 추세 검정력을 깎는다(§4). 둘 다 권고하지 않는다.
5. **2-arm 안의 x_lo 규칙 변경**은 데이터를 본 뒤 1차 estimand의 정의 조건을 바꾸는 일이다. J1에서 fused와 fused_sym의 A λ\*가 서로 달랐다는 것을 이미 알고 있으므로 감사 대상이다. 3-arm(S2f)은 이 표면이 없다.

## 7. 권고

**S2f** (TP-only, 3-arm, A·B, N = 2, 4, 8, Job 3개, 각 Job에 N=1 앵커, J1·rev12 DP 재사용, J1 재실행 없음).
- 비용 [유도]: 예약 70.9 GPU-h, 사용 60.9 GPU-h(86%), 최장 5.18 h(M1a). 범위는 M0 54.0 GPU-h·3.98 h부터 M1 76.2 GPU-h·5.55 h까지이고, 봉인 forecast 최악은 J2 7.67 h다. S0 대비 예약 GPU-h는 같은 보정끼리 M0 기준 72%(190.0 → 54.0), M1a 기준 76%(296.8 → 70.9) 줄어든다 [유도].
- 이유:
  - (1) 1차 estimand G_sym의 TP 추세가 4점(N = 1, 2, 4, 8)으로 온전히 남고, P9·P10·P11 규칙 문언을 바꾸지 않는다(x_lo·확장·앵커 규칙 불변).
  - (2) X는 이미 P9-a로 죽었고 U12상 A·B와 독립이라 빼도 판정 손실이 없다.
  - (3) DP는 같은 바이트의 rev12 Job에서 이미 측정됐다. 재사용하면 DP 재측정 70.9 GPU-h(S9f)를 아낀다.
  - (4) 모든 Job이 9.5 h 정지보다 4.3 h 이상 짧다.
  - (5) S2(2-arm, 53.3 GPU-h)보다 17.6 GPU-h 비싸지만 x_lo 규칙 변경, LO 정의 혼합, G_def 상실이 없다.
- **진행 조건(순서대로)**:
  - ① J2·J4·J8 fetch가 sha256까지 통과하고, 세 Job 모두에서 DP의 fused_sym·agnostic(그리고 x_lo 출처 fused) boot1·boot1ext·boot2가 rc 0이며 셀 파일이 완결이어야 한다. 이 판정은 값을 보지 않고 한다. 실패한 N에는 S9f 해당 Job을 더한다(J2 10.4 · J4 20.7 · J8 39.9 GPU-h [유도]).
  - ② rev13에 §6 항목을 등록하고 규칙층 감사를 받는다. xcheck FAIL이 B에 미치는 함의가 감사 질문이다.
  - ③ 측정 경로 바이트 불변을 하네스층 감사에서 확인하고 재봉인한다.
  - ④ CPU preflight → dry-run(`job-table`이 이 문서의 M0 값을 재현하는지 대조) → 사용자 승인.
- **9.5 h 정지 원인**은 rev13 캡을 정하기 전에 확인한다. 공통 상한이라면 J_N 캡을 그 아래로 등록한다.
