# 사전등록 — **B6 적격 창(eligible window) 실현 가능성**: rev7의 예산 승인 선행 조건

**2026-08-22 (2차 세션)** · 메인 세션 · GPU 지출 **0**(제출 0건) · 새 성능 판정 **0건**.

> **왜 이 문서만 따로 있는가.** rev6 규칙층 감사
> [`audit_kernel_mech_rev6_2026-08-22/VERDICT.md`](audit_kernel_mech_rev6_2026-08-22/VERDICT.md)
> 는 `NO-GO`(차단 B1–B7)를 내면서 예산 판단을 **B6 하나에 걸었다**:
> *"예약 ≈1.0–1.4 GPU-hr는 **B6가 P6로 값과 함께 사전등록되는 조건에서** 값한다 …
> **B6가 안 닫히면 D=92 셀이 통째로 폐기 → 1차 비교쌍 소멸 → 전액 손실**."*
> ⇒ **B6를 먼저 닫지 못하면 나머지 6건(B1–B5·B7) 수리는 무의미하다.** 이 문서는 B6만 다룬다.
>
> ★**이 문서는 rev7이 아니다.** B1–B5·B7은 **닫히지 않았고**, 이 문서로 닫히지도 않는다.
> rev7 착수 여부는 이 판정 위에서 별도로 결정한다.

## 1. B6가 물은 것

> `out=128`+`CONC=16` closed-loop면 평균 **8 step마다** 재활용→prefill 발생, 기준은 창 안
> prefill **0개**·**≥20 step** ⇒ `P ≈ (7/8)²⁰ ≈ 0.07`. … `--disable-radix-cache` 미고정이
> 이를 자릿수로 뒤집는다. `out` 선택 근거 0줄. **P6 통과 기준을 값으로 사전등록할 것.**

---

## 2. ★ 집계 단위를 먼저 정한다 (교훈 #5)

감사의 `P ≈ 0.07`은 **간극 하나가 ≥20 step일 확률**이다. 그러나 **결정에 쓰이는 양은 그것이
아니다** — rev6 §4가 요구하는 것은 *"셀당 적격 창 **≥10개**"* 이므로 결정량은

```
N_win(cell) = 한 셀(= D 값 하나)에서 얻는 적격 창의 개수
판정        = P( 3개 셀 전부 N_win ≥ 10 )        ← ★캠페인 전액이 걸린 양
```

이다. 확률 0.07을 "희소하다"로 읽으면 과대 비관이고, 기대 개수만 보면 과대 낙관이다.
**둘 다 아니라 위 결합확률로 판정한다.**

## 3. rev6이 쓴 워크로드 그대로면 — ★**통과 못 한다**

가정: 비동기 closed-loop(요청 완료 즉시 새 요청 투입), `CONC=16`, `out=128`, `NP=200`.
정상상태 완료율 = `CONC/out` = **0.125 prefill/step**. prefill 하나가 decode step `b`개를
가린다고 두면 적격 간극은 `P = (1−0.125)^(20+b)`, 개수는 `Binomial(NP, P)`.

| NP | b | E[창/셀] | P(셀 ≥10) | ★P(3셀 전부 ≥10) | 셀당 decode step |
|---|---|---|---|---|---|
| 200 | 0 | 13.84 | 0.891 | **0.708** | 1,600 |
| 200 | **2** | 10.60 | 0.619 | ★**0.238** | 1,600 |
| 400 | 0 | 27.68 | 1.000 | 1.000 | 3,200 |
| 400 | 2 | 21.20 | 0.998 | 0.994 | 3,200 |

★**`b=2`(prefill이 decode step 2개를 가림)에서 캠페인 전액 손실 확률이 76%다.** 게다가 이
표는 rev6 §4의 나머지 조건 **(b) 단일 stream group · (d) 정상상태**를 **가격에 넣지 않았다** —
둘 다 개수를 **줄이기만** 한다. ⇒ **감사의 경보는 옳았고, rev6 워크로드는 이 기준으로 사면
안 된다.**

## 4. 두 가지 수리와 값

### (i) `NP`를 400으로 — 확률로 사는 방법
`P(3셀 전부) = 0.994`(b=2). 대가: 셀당 decode step **2배**(1,600→3,200). D=16에서
ITL≈120 ms 가정 시 부팅당 벤치가 **+192 s** — 부팅 상수(**145.8 s**, gate #13 실측)보다 크다.
★**여전히 확률적**이고 (b)(d)를 안 샀다.

### (ii) ★**batch-synchronous 라운드** — 구조로 사는 방법 (**등록안**)

**`NP = CONC = 16`인 벤치를 한 부팅 안에서 `R`회 반복한다.** 라운드 하나는
*프리필 16개 동시 → 전원 `out` 토큰 디코드 → 전원 종료 → 다음 라운드*.
`ignore_eos`가 **기본 True**(`bench_serving.py:250-252`, `--disable-ignore-eos` 미지정)이므로
16개 요청이 **정확히 같은 step 수**를 돌고, 라운드 내내 `decode_running_batch_size ≡ 16`이다.

⇒ 라운드 하나가 **prefill-free run 하나를 결정론적으로 생산**한다. 확률이 사라진다.

| 얻는 것 | rev6 대비 |
|---|---|
| (a) 창 안 prefill 커널 0개 | **구조로 보장**(라운드 안에 새 요청이 없다) |
| (c) `decode_running_batch_size > 0` | **구조로 보장**(≡16) |
| (d) 정상상태(배치 선형추세 ≈0) | **구조로 보장**(배치가 상수) |
| ★**배치 등가**(비교 셀 간 배치 중앙값 차 ≤1) | rev6 §5는 *"보고만 하고 미충족이어도 판정 계속"* 이었다 — 이제 **세 셀 모두 정확히 16**이라 **조건이 사라진다** |
| (b) 단일 green-ctx stream group | ★**보장되지 않는다** — §5 참조 |

## 5. ★ 창의 정의 — 하나의 run을 6개로 쪼개지 않는다

`out=128`이면 라운드당 prefill-free run이 **~125 step**이다. 이를 20-step 창 **6개**로 세면
`N_win`이 6배가 되지만, 그 6개는 **같은 run·같은 부팅**에서 나온 것이라 독립이 아니다 —
부팅×창 2단 BCa 부트스트랩(rev6 §3.4)의 창 층 `n`을 인위적으로 부풀려 **분산을 과소추정**한다.

★**등록**: **창 = 하나의 maximal prefill-free run = 하나의 라운드.**
**분석 구간 = 그 run에서 rev6 §4 (a)(b)(c)(d)를 **동시에** 만족하는 첫 20 decode step.**

`(b)`가 왜 자동이 아닌가: 라운드 사이에 decode batch가 **비므로**
`multiplexing_mixin.py:915-923`이 sticky를 유지하지 않고 `set_current_stream_idx(0)`으로
떨어뜨린다(rev6 §4(b)가 인용한 코드 사실). ⇒ 라운드 **첫 몇 step은 목표 D가 아닌 파티션에서
돌 수 있다**. 그래서 분석 구간의 시작점을 **고정 상수 `c`로 두지 않고** `E2_SINGLE_GROUP` +
`E1_NO_PREFILL_KERNEL` assert가 처음 연속 20 step 성립하는 지점으로 **관측이 정하게** 한다
(자유 모수 추가 0개).
★**이것이 `out`을 128로 유지하는 이유다** — run이 ~125 step이라 20 step을 확보하고도
**105 step의 여유**가 있어 sticky 재확립 지연을 흡수한다. `out`을 줄이면 이 여유가 사라진다.
(rev6가 `out=128`을 고른 근거는 0줄이었다 — 이 문서가 **사후에 근거를 부여**하는 것이며,
값 자체는 rev6에서 **바꾸지 않았다**.)

## 6. ★ 등록하는 P6 통과 기준 (값)

**Stage 0′ 프로브 P6**(≥3 부팅, 본 캠페인 전):

| 항목 | 등록값 |
|---|---|
| 라운드/부팅 | **`R = 5`** |
| 셀당 부팅 | 4 (rev6 §5 불변) |
| ★**예측 `N_win`/셀** | **20** = 5 × 4 |
| ★**P6 통과 기준** | 각 셀 `N_win ≥ 10` ⇒ 예측 대비 **여유 2.0배** |
| 창당 분석 step | **20**(rev6 §3.5 등록값 불변) |
| 실패 시 | **중단**(campaign 미제출). ★가설 반증이 아니라 **측정 조건 미충족**(교훈 #21) |
| 보고 필수 | 셀별 `N_win` · run 길이 분포 · 각 run에서 `(a)(b)(c)(d)` 성립까지 걸린 step 수 |

**추가 벽시계**(라운드 5회, ITL 가정 D=16/44/92 = 120/60/40 ms):
`5 × 128 step` = **77 / 38 / 26 s per 부팅**. 부팅 상수 145.8 s 대비 **+53%/+26%/+18%**,
16 부팅 기준 총 **+0.20 GPU-hr** 이내. ⇒ rev6 예약 **1.0–1.4 GPU-hr 안에 들어간다.**

★**`--disable-radix-cache`를 고정한다**(켬 = 캐시 끔). 근거 2개:
(1) 저장소 캠페인 **97개 `.sbatch` 전부**가 이 플래그를 쓴다 — L1 비교가능성의 basis.
(2) `L=1024` **고정 프롬프트**라 캐시를 켜면 2라운드부터 prefix hit로 prefill이 사실상 사라져
**적격 창이 공짜로 생긴다** — 그건 창을 **버는 것이 아니라 측정 대상을 바꾸는 것**이고
(hybrid arm에서 KV/mamba 상태 공유 거동까지 건드린다), 무엇보다 §4-(ii)가 이미 창을 구조로
확보하므로 **필요가 없다**. ⇒ 캐시의 도움을 받지 않는다.

## 8. ★ 이 설계가 잃는 것 (반드시 병기)

1. ★**동거(cohabitation)가 완전히 사라진다.** rev6은 이미 prefill 주입을 제거해 cell A를
   "비동거 자연 상태"로 만들었는데, batch-synchronous는 그것을 **한 걸음 더** 밀어 라운드 내
   prefill을 **0으로 강제**한다. ⇒ **이 캠페인의 decode step 분해는 "prefill과 동거하지 않는
   decode"의 분해다.** 운영점(PD-mux가 실제로 겹쳐 도는 상태)으로 이식 금지 — rev7 §7에
   **문장으로** 등재해야 한다.
2. **도착 과정이 사라진다** — 큐 깊이·admission 동역학이 없다. 정책·SLO 문장 전면 금지.
3. **라운드 경계 효과가 새로 생긴다**(sticky 재확립·KV 풀 재사용). §5의 assert가 그것을
   분석 구간 **밖으로** 밀어내지만, 밀어냈다는 사실 자체를 보고해야 한다(§6 보고 필수 3번째).
4. 배치가 정확히 16으로 **고정**되므로, 배치 축의 어떤 결론도 이 캠페인에서 나오지 않는다.

## 9. 판정

**B6는 닫힌다 — 단, rev6이 등록한 워크로드로는 닫히지 않는다.**

* rev6 워크로드 그대로: **P(3셀 전부 통과) = 0.238**(b=2) ⇒ ★**그 형태로는 사면 안 된다.**
  감사의 경보는 옳았다.
* §4-(ii) batch-synchronous + §6 등록값(`R=5`): 예측 `N_win` = **20/셀**, 요구 10 대비
  **2.0배**, 추가 비용 **≤0.20 GPU-hr**, 그리고 (a)(c)(d)와 배치 등가가 **확률이 아니라
  구조로** 성립한다.
* 대가는 §8 — 특히 **동거의 완전한 소멸**이며, 이것은 비용이지 결함이 아니다(rev6이 이미
  그 방향으로 갔다). ★**다만 rev7 §7에 명문화되지 않으면 이 문서의 통과는 무효다.**

★**이 판정이 닫지 않는 것**: **B1·B2·B3·B4·B5·B7**(분모 불일치 · `U_infl` 대수 · 자유 모수
"전수" 오류 · 1차 작동특성 0건 · "스텝 경계" 미정의 + `A3` 항등식 · 프로브 정의가 재사용
금지된 rev5에만 존재) — 전부 **불변**이고, **NVTX 엔진 패치**(`grep -rn nvtx src/` = 0건)라는
선행조건도 그대로다. ⇒ **rev7은 여전히 `NO-GO` 상태다.** 이 문서는 그 중 **예산 판단을 걸어
둔 항목 하나**를 값으로 닫았을 뿐이다.
