## 0. 이 실험이 바꾸는 것 — payoff 먼저 (게이트 #28)

정본의 실무 권고는 **"peak decode 부하 기준 decode-heavy static 고정"** 이다. 그 권고는
**SM 분할 축에서만 최적화**해 얻어졌다. 그런데 **admission 축(`--max-running-requests`)은
저장소 전체에서 한 번도 변수가 아니었다** — `.sbatch` **66개가 전부 `48`로 하드와이어**돼
있고(§1-4), 그 `48`은 이 기판·이 워크로드와 무관하게 고정된 상수다.

⇒ **바꿀 수 있는 것은 정확히 하나**: 권고를 *"(SM 분할, admission cap)의 **결합** 최적점"*
으로 다시 쓸 것인가, 아니면 *"admission 축은 이 기판에서 무력하다"* 는 **정보 있는 음성**으로
`CONSENSUS.md` §5-8(b)의 **admission 갈래를 닫을** 것인가.

★**이 실험이 하지 않는 것**(먼저 못 박는다):
* **HE0를 되살리지 않는다.** cap은 **static 설정값**이고 이 설계에 동적 컨트롤러는 없다.
  결과가 어느 방향이든 *"동적 제어가 best-static을 넘는다"* 로 읽을 수 없다.
* **SM 분할 축의 결론을 건드리지 않는다.** layer-type 死·PD 분리 이득·gate #13/#16 전부 불변.
* cap이 이기더라도 그것은 **다른 축의 static 튜닝**이지 새로운 제어 기법이 아니다.

## 1. 코드 사실 (2026-08-23 직접 확인, file:line)

1. **admission 게이트의 실체.** `managers/scheduler.py:2296-2299`
   `get_num_allocatable_reqs(running_bs) = pp_max_micro_batch_size − running_bs`,
   그리고 `:667-671`에서 `pp_max_micro_batch_size := max(max_running_requests // pp_size, 1)`.
   `:2364-2371`·`:2432-2434`에서 이 값이 `≤ 0`이면 `running_batch.batch_is_full = True`가
   되고 **prefill 배치가 만들어지지 않는다**.
   ⇒ ★**§1-4 kill chain의 마지막 마디**(*"batch 정체 → prefill admission 차단 → TTFT 폭발"*)
   **가 정확히 이 한 줄이다.** 死因이 SM 분할이 아니라 **공유 running-batch capacity**라는
   정본 진술과 코드가 일치한다.
2. **cap이 hybrid arm에서 두 축을 동시에 움직인다(앨리어스).**
   `model_executor/model_runner_kv_cache_mixin.py:218-232`:
   `max_mamba_cache_size`가 명시되면 그 값을 쓰고(`:218`), **명시되지 않았고**
   `disable_radix_cache ∧ max_running_requests is not None`이면
   **`max_mamba_cache_size := max_running_requests`**(`:224-229`).
   ⇒ 저장소의 모든 캠페인이 `--disable-radix-cache` + `--max-running-requests 48`이므로
   **SSM 포함 arm에서 mamba state pool은 지금까지 항상 48이었고 cap과 구별 불가능했다.**
   이것은 `CONSENSUS.md` §3-23이 이미 등재한 코드 사실이다(이 문서는 재확인만 했다).
3. **저장소 전역 상수.** `.sbatch` 중 `--max-running-requests 48`을 쓰는 파일 **66개**,
   `--max-mamba-cache-size`를 지정하는 파일 **6개**(전부 `s8_frontier`/`s2_sticky`/
   `sticky_smoke` 계열). ⇒ **정본 결론을 만든 캠페인 계열(slo_sched·g2_0·s8)에서 cap은
   변수였던 적이 없다.**

## 2. 선행 연구 — ★**"구현조차 되지 않았다"는 절반만 맞다**

`CONSENSUS.md` §5-8(b)는 *"admission-control 또는 KV-aware한 lever로 이 死因을 직접 겨냥하는
시도는 **구현조차 되지 않았다**"* 라고 적는다. **레버·컨트롤러로서는 사실이다.** 그러나
**cap 스윕 자체는 한 번 돌았다** — 이 문서를 쓰기 전에 grep으로 확인했고, 그것을 모른 채
설계했다면 게이트 #18(*"저장소가 같은 진단을 두 번 냈는데 정본이 안 바뀌면 도구 규율
실패"*)의 재발이었을 것이다.

**`s8_frontier/batchcap.sbatch`, job 870301** — arm **T8**, cell `d16`/`d44`,
cap `{48, 96, 192}`, rate 16, NP=128, seed 1–4.
★**이 캠페인의 목적은 정책 비교가 아니라 "ITL 천장이 설정 속성인가"** 였다.

★**이미 확립된 것**(설계 동기로만 인용 — claims-auditor 미통과, **판정 근거 아님**):
* `max decode_running_batch_size`가 **정확히 cap(48)에서 멈추고** 그 시점
  `kv_occupancy ≈ 0.018–0.024` ⇒ ★**배치를 묶는 것은 메모리가 아니라 설정값**이다.
  (E-B1 규칙층 감사가 별도로 관측한 *"`max_running_requests=48`이 전 28부팅에서 decode
  배치를 하드캡한다"* 와 **독립적으로 같은 방향**이다.)
* d16에서 cap을 올리면 **TTFT p95가 자릿수로 내려가고 ITL p95는 올라간다**(SLO 50ms 기준
  `frac_itl_le_50`이 0.98→0.3대로 붕괴). d44에서는 **cap을 4배로 올려도 TTFT·ITL이 사실상
  불변**. ⇒ ★**cap 레버의 효력이 SM 분할에 강하게 의존한다**(prefill-heavy에서 강, decode-heavy
  에서 ≈0).

★**확립되지 않은 것(= 이 설계가 존재하는 이유), 전수**:
1. **arm**: T8(순수 Transformer) 단독. §3-23 코드 사실에 의해 **hybrid로 이식 불가**
   (hybrid에서 cap은 mamba pool도 같이 움직인다).
2. **결정량**: `frac_itl_le_50/60`은 정본 goodput(**요청별 TTFT ≤ SLO ∧ 요청-내부 token-ITL
   p95 ≤ SLO**)이 아니다. TTFT·ITL을 **결합한 판정이 없다.**
3. **워크로드**: 정상 rate 16 단일점 — 정책 비교용으로 **폐기된 형태**(방법론 게이트 #2,
   "정책 비교는 변화 trace").
4. **셀 타당성**: `d16` 셀은 decode-active 시간의 **18%만** 목표 파티션에 있었다
   (나머지는 108로 auto-revert, `CONSENSUS.md` §1-22). ⇒ 그 셀의 라벨을 믿을 수 없다.
5. **분산 구조**: seed 4개가 **같은 부팅 안**이다. gate #13 job-축 캠페인이 확립한
   부팅-층 분산이 표집되지 않았다.
6. **decode-heavy 운영점에서의 결합 최적점**: cap×SM **격자가 없다**(각 cell에서 cap만 훑음).

## 3. ★ 이 설계가 반드시 먼저 깨야 하는 앨리어스

hybrid arm에서 `cap`을 움직이면 `max_mamba_cache_size`가 따라 움직인다(§1-2). 그대로 스윕하면
*"admission을 조였다"* 와 *"SSM state pool을 줄였다"* 가 **구별되지 않는다.**

★**해소**: **`--max-mamba-cache-size := C_max`(스윕 최대 cap)로 전 arm·전 셀에 고정**하고
`--max-running-requests`만 움직인다. 그러면
* pool 크기가 **cap과 무관한 상수**가 되어 admission 축이 **단독으로** 움직이고,
* `kv_mamba_occupancy = batch / C_max < 1`이 되어 §3-23이 지적한 **항등식(`≡1.0`)이 깨진다**
  — 그 지표가 이 캠페인에서 처음으로 정보를 갖는다.

★**주의(§3-23의 원 권고와 방향이 다르다)**: §3-23은 *arm 간* 교락을 피하려고 *"고정은 전
arm 공통 절대상수가 아니라 `= cap` 규칙이어야 한다"* 고 적었다. 그것은 **arm을 비교할 때**의
규칙이고, 이 설계는 **한 arm 안에서 cap을 비교**하므로 **정반대의 고정이 필요하다**(pool 상수,
cap 변수). ⇒ **NSL-1은 단일 arm 안에서만 비교하고 arm 간 비교를 하지 않는다**(§6-1).
★단일 arm 제한은 이 고정의 **논리적 귀결**이지 편의가 아니다.

★**메모리 실현 가능성은 가정이 아니라 프로브 대상**: slot당 SSM state 비용이 arm마다 다르고
(M8 0.255 / Ha8 0.141 / Hs8 0.096 GB) pool을 `C_max`로 키우면 그만큼 attention KV pool에서
빠진다. **`C_max`에서 부팅이 되는지, KV pool이 얼마나 남는지는 Stage 0 프로브 P1이 잰다**
(§5). 부팅 실패는 **가설 반증이 아니라 측정 조건 미충족**이다(게이트 #21).

## 4. 결정량과 격자

### 4.1 결정량 (1개)

**정본 goodput** = 요청별 (`TTFT ≤ TTFT_SLO`) **AND** (요청-내부 token-ITL p95 ≤ `ITL_SLO`)
를 만족한 요청 비율. mean-ITL은 secondary(방법론 게이트 #4).

```
결정량:  argmax_{(D, cap)} goodput   vs   argmax_{D} goodput | cap = 48
판정:    (i) 결합 argmax의 cap ≠ 48  →  ADMISSION_AXIS_MATTERS
        (ii) 결합 argmax의 cap = 48  →  ADMISSION_AXIS_INERT (정보 있는 음성)
        (iii) 페어드 CI가 0을 포함    →  UNDETERMINED
```
★**"이긴다"의 문턱은 새로 만들지 않는다** — 정본 방법론 게이트 #3(*"3% 미만 차이는 headline
아님"*)과 페어드 부트스트랩 CI를 그대로 쓴다.

★이것이 Stage 0 프로브 **P2**다. 확인 실패 시 **rate를 바꾸는 것이 아니라 설계를 되돌린다**

### 4.4 ★ 검정력 — **수입값 없이, 필요조건 형태로**(`nsl1_power.py` → `NSL1_POWER_2026-08-23.json`)

그보다 크면 비용이 **초선형으로 폭발**한다(SD가 5배면 n은 20배, 부팅만으로 30 GPU-hr —

* SD가 크면 선택지는 (i) 격자 축소(예: `D` 2점 × cap 2점 = 4셀) (ii) 효과 크기 재정의

* ★**이 표는 어떤 관측도 아니다** — 부과된 goodput 수준 위의 계산이다. `4.8 pp` 행은
  "이런 크기면 이렇게 된다"를 보이는 **예시 눈금**이지 이 기판의 측정값이 아니다.

## 5. Stage 0 프로브 (스모크 = 게이트 #26) — 본 캠페인 **이전**

| **P4** | ★**셀 타당성**: 목표 파티션 체류 시간 비율. 선행 job 870301의 `d16` 셀은 **18%**였다(§2-4) | 해당 셀 **폐기**(측정 실패로 기록) |
| ★**P6** | ★**부팅-층 goodput SD를 잰다**(한 셀, 변화 trace, n≥4 서로 다른 job). §4.4의 상한 **0.88 pp**(goodput 70pp 기준)와 비교 | ★**SD > 상한이면 본 캠페인 미제출** — 격자 축소·표적 재정의·보류 중 하나를 **먼저** 결정한다. 측정 조건이지 반증 아님 |

## 6. 닫지 **않는** 것 (스코프)

1. **arm 간 비교 금지** — §3의 pool 고정이 arm마다 다른 메모리 분할을 강제한다. NSL-1은
   Ha8 **안에서만** 말한다. *"hybrid는 …"* 라고 쓸 수 없다.
2. **역할 인지(role-aware) admission은 이 설계에 없다.** `get_num_allocatable_reqs`는
   스칼라 하나다. *"decode 슬롯을 예약한다"* 는 **엔진 패치**가 필요하고, **스칼라 cap이
   먼저 움직이는지 확인되기 전에는 짓지 않는다**(짓고 나서 레버가 무력하면 전액 손실).
   ⇒ NSL-2의 전제조건이 NSL-1의 결과다.
3. **KV-aware 갈래는 이 설계로 열리지 않는다.** 정본은 이 regime(ctx 4k)에서
   attention KV가 구속 근처에 간 적이 없다고 적고 있고(그 관측치 자체가 인용 금지),
   선행 job 870301도 `kv_occupancy ≈ 0.02`를 봤다. ⇒ **NSL-1은 admission 갈래만** 다룬다.
   §5-8(b)의 KV 갈래는 **열린 채로 둔다**.
4. **동적 제어 0개** — HE0 불변(§0).
5. **cudagraph-ON 운영점 고정**, 단일 노드, 단일 SLO 쌍, `ctx=4096`.
6. ★**선행 job 870301의 수치는 설계 동기로만 인용**한다. claims-auditor 미통과이고
   셀 타당성 결함(§2-4)이 있으므로 **판정 근거·비교 기준으로 재사용 금지**.
7. **gate #13/#16 전진 0 · switch-cost 트랙 무관 · C2 인용정지 (a)(b) 승계.**

## 8. 감사 의뢰 (게이트 #37 — 합격 기준을 함께 준다)

> **단일 질문**: *"cap(admission) 축을 SM 축과 **결합 격자**로 재는 이 설계가, (i) §1-4가

> 만드는가?"*

**먼저 깨뜨릴 곳**:

2. **결정량이 항등식이 아닌가** — `argmax`가 데이터와 무관하게 정해지는 격자 선택이

   Stage 0 P6)이 정당한가 — 아니면 *"SD를 모른 채 격자를 등록한 것"* 자체가 차단인가?
   ★부수 질문: unpaired 가정이 맞는가(부팅 간 페어링이 정말 구조적으로 불가능한가),
