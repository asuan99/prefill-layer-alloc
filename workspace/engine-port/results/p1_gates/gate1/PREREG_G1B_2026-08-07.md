# G1-b — telemetry 재현런을 rate {2,3,4,6}로 확장 (Gate 1의 후속 gate)

작성: 2026-08-07 (experiment-runner), 제출 **전** 고정. 결과를 본 뒤 이 문서의 결정 규칙을
바꾸지 않는다(CLAUDE.md 방법론 게이트, `PROJECT_STATUS.md` 방법론 게이트 #8).

## 동기

`reports/CONSENSUS.md` §1-1(rev14)는 job 874478(Gate 1)의 결과로 다음 문장을 정본에
추가했다:

> **★실질 산출 1 — 이 격자에서 정책은 단일 분할에 고정됐다**: 전 런
> `decode_running_batch_size` 최댓값 **23**(문턱 `decode_bs_divisor=36`) ⇒ **`(54,54)`는
> 0회 선택**. 인용 가능한 파티션 수치는 **`(74,34)` 하나뿐**이다.

이 문장은 **rate 2·3에서만** 측정됐다(Gate 1 PREREG의 예산 축소). 그러나 §1-1이 인용하는
성능 캠페인 873944(2026-08-05, P1 운영점 대조)의 실제 격자는
`MAIN_RATES="2 3 4 6"`(`results/p1_opint/p1op_run.sbatch:45`)이고, §1-1의 인용 가능
정량치 3개 중 하나가 **Granite rate4**다(Zamba2는 인용 가능 수치가 rate2·rate3뿐이지만,
"단일 분할 고정" 문장 자체는 rate 한정 없이 "이 격자에서"라고 쓰여 있어 독자가 격자 전체
{2,3,4,6}에 적용된다고 오독할 위험이 있다). rate가 오르면 decode 배치가 커지고,
`decode_bs_divisor=36`을 넘으면 `stream_idx`가 2로 바뀌어 `(54,54)`가 선택 가능해진다
(코드 확인, 아래 "결정량이 항등식이 아닌 이유" 참조). G1-b는 이 문장을 rate 4·6에서
직접 반증 시도한다.

## ★ 이 게이트가 Gate 1 본체와 다른 점 (필수 명시)

Gate 1의 주 조건(pop A frac ≥ 0.90)은 claims-auditor 감사로 **코드 항등식**임이 확인됐다
(`multiplexing_mixin.py:881-909`의 `if not self.running_batch.is_empty() and
self.split_prefill_batch:` 분기가 정확히 telemetry의 `prefill_active_batch_size>0`을
만드는 상태이므로, "decode-busy ∧ prefill in-flight일 때 idx∈{1,2}"는 관측 가능한 반례
상태가 없다 — `CONSENSUS.md` §1-1 Gate 1 블록, §3 항목28).

**G1-b의 결정량은 이 항등식과 다르다.** 코드는 다음만 결정한다:

```
stream_idx = max(1, min(2, decode_running_batch_size * 2 // decode_bs_divisor))
# decode_bs_divisor = 36 (pdmux_a100_smoke.yml)
# stream_idx == 2 (-> (54,54))  iff  decode_running_batch_size >= 36
```

이 자체는 산술 항등식이지만, **`decode_running_batch_size`가 36을 넘는지 자체는 코드가
정하지 않는다** — 워크로드(요청 도착률, 서비스 시간, 큐잉 동역학)가 정하는 **경험적
사실**이다. rate를 올리면 decode 배치가 커질 것이라는 것은 정성적 기대일 뿐, "36을
넘는다/안 넘는다"는 이 실행을 실제로 관측하기 전까지 결정돼 있지 않다. ⇒ **이 gate는
Gate 1의 주 조건과 달리 진짜 판별력이 있다.** (Gate 1의 판별력은 오직 negative control
B/C에서만 나왔다 — 이번에도 B/C를 계속 병기하지만, 이번 gate의 **주 결정량**은 A 자체다.)

## 사전등록 판정 규칙 (제출 전 고정)

### 주 결정량

각 rate 창에서:
1. `max(decode_running_batch_size)` (창 내 전체 benchmark-phase 스냅샷 기준, population
   A로 필터링하지 않음 — decode 배치가 36을 넘었는지는 A/B/C 어느 population에 속하는지와
   무관하게 워크로드 전체의 사실이다).
2. population A(decode-busy ∧ prefill in-flight)의 **시간가중** `(prefill_sms,
   decode_sms)` 히스토그램, 특히 `frac((54,54))`.

### 집계 단위 (primary = 시간가중, 이유)

Gate 1과 동일하게 **시간가중을 primary**로 채택한다. 이유: 우리가 묻는 것은 "decode-busy
∧ prefill-in-flight로 실제 보낸 **시간** 중 얼마가 `(54,54)`로 라벨됐는가"이지, 스냅샷
**개수**의 비율이 아니다 — event-loop iteration 길이는 prefill/decode 배치 크기에 따라
수십 배 차이 나므로(Gate 1 PREREG가 이미 확립한 이유, 동일 정신) 개수가중은 짧은
iteration을 체계적으로 과대표집한다. `PDMUX_TRACE_FORCE_PREFILL=1`이 개수가중 통계를
prefill 쪽으로 편향시키는 것도 Gate 1과 동일하므로, **개수가중은 참고용으로만** 병기한다
(`gate1b_analyze.py`가 이미 두 값을 모두 출력한다).

### 철회 규칙 (사전 고정, 결과를 본 뒤 바꾸지 않음)

- **철회**: rate 4 또는 rate 6의 population A에서 `(54,54)`가 **시간가중 1% 이상**
  (`frac_5454 >= 0.01`) 나타나면, 정본 rev14의 "이 격자에서 정책은 단일 분할에
  고정됐다"/"`(54,54)`는 0회 선택" 문장을 **즉시 철회 대상**으로 보고한다. 이 임계값은
  `gate1b_analyze.py`의 `WITHDRAWAL_THRESHOLD = 0.01`에 하드코딩돼 있다(방법론 게이트 #8
  — 실행 스크립트에 결과를 보기 전 고정값으로 박아 둔다).
- **TRACE**(철회 아님, 단서만 추가): `0 < frac_5454 < 0.01`이면, "고정" 문장은 유지하되
  "그러나 rate 4·6에서 극소량(≤1%) 관측됨, 정확한 값은 결과 참조"라는 각주를 추가한다.
- **확장**: rate 4·6 둘 다 `max(decode_running_batch_size) < 36`이고 `frac_5454 == 0`이면,
  "단일 분할 고정" 문장의 **스코프를 873944 전 격자(rate 2–6)로 확장**한다. 단
  스코프는 여전히 **Zamba2-2.7B + 이 워크로드(in2000/out96, ctx4096, triton) 한정**이다
  (Granite는 미측정 — 방법론 게이트 #11, 격자/모델 간 이전 금지).

### 양성대조 (필수 — 실패 시 rate 4·6 수치를 해석하지 않는다)

rate 2·3이 874478을 재현하는지 확인한다:
- **판정 조건**: `pop_A_time_weighted_frac >= 0.90` **그리고** `max(decode_running_batch_size)
  <= 30`(874478의 관측값 rate2=9, rate3=23 근방 — 여유를 둔 상한, `gate1b_analyze.py`의
  `G1B_POSCTRL` 블록에 하드코딩).
- **재현 실패 시**: rate 4·6의 수치는 **해석하지 않는다**(`gate1b_analyze.py`가 이
  경우 `G1B_RULE` 블록에서 자동으로 "POSITIVE CONTROL FAILED, not interpreted"를 출력
  하도록 이미 구현돼 있다 — 결과를 본 뒤 이 로직을 바꾸지 않는다).
- 이 판정은 **874478의 정확한 수치 재현(bit-identical)을 요구하지 않는다** — n=1 단일
  샘플이고 노드가 다를 수 있어(874478=gpu38) 약간의 편차는 예상되지만, 정성적으로
  같은 패턴(pop A 거의 전부 `(74,34)`, decode_bs가 36 밑)이어야 한다.

### 음성대조 (Gate 1과 동일한 caveat 유지)

population B(decode-idle)·C(decode-busy, prefill NOT in-flight)를 rate별로 보고한다.
Gate 1 감사가 확정한 caveat을 그대로 승계한다:
- **C의 절대 수치(0.97xx류)는 인용 금지**다 — 감사가 "few-snapshot(10개 수준) 위에
  있고 dt가 4–10배 부풀려졌다"고 확정했다(`CONSENSUS.md` §1-1 Gate 1 블록의 인용 금지
  목록). 개수(n_snapshots)·에피소드 수만 보고하고, 정량치 자체를 새 결론의 근거로
  쓰지 않는다.
- B는 Gate 1과 마찬가지로 §1-22 auto-revert(`(108,0)`)를 재확인하는 용도로만 병기한다.

### 필수 게이트

- **커버리지 가드**(각 rate 창 `telemetry_coverage >= 0.98`). rate 4·6은 창이 짧고
  이벤트가 조밀해 유실 위험이 있다(874465 사후분석이 보여준 tail-truncation 실패
  모드). **실패하면 그 창은 `UNMEASURABLE`로 보고하고, 케이던스를 바꿔 통과시키려
  하지 않는다** — 케이던스 변경은 양성대조(rate 2·3)를 무효화한다.
- **grid-completeness 검정**(Gate 1 감사 권고, 이번에 신규 구현 — `gate1b_analyze.py`의
  `grid_completeness()`): `trace_forced==False ⟹ sample_index==1 ∨ sample_index % 32
  == 0`을 모든 관측 행에서 확인(위반 시 `violations` 카운트, 0이어야 정상)하고, **각
  rate 창의 [min_sample_index, max_sample_index] 범위 안에서 기대되는 스케줄 그리드
  포인트 중 결측된 개수**를 출력한다(`missing`). 이 검정은 tail-only인 coverage와
  달리 **창 중간의 결측**을 잡는다 — 874478 재분석(본 사전등록 준비 중 검증)에서 rate2
  창은 expected=11,959/missing=0, rate3 창은 expected=5,683/missing=0으로 확인했고,
  전체 파일 기준으로는 `gate1_result_874478.txt`가 이미 보고한 "결측 0/22,252"의
  근거가 이 검정이었음을 재현으로 확인했다(구현 세부: `sample_index`는 서버 프로세스
  전체에 걸친 단조증가 카운터로, rate 창 경계에서 리셋되지 않으므로 기대 그리드는
  창 자신의 관측 범위에 앵커해야 한다 — 0부터 시작하는 전역 범위를 쓰면 창 시작
  이전의 그리드 포인트까지 "결측"으로 오탐한다는 것을 초안 구현에서 직접 확인·수정).
- `dropped_events`는 자기 실패에 검열되므로(Gate 1 addendum이 이미 확정) **이 게이트의
  근거로 쓰지 않는다** — 값은 기록만 한다(`gate1b_analyze.py`는 이 필드를 판정에
  쓰지 않는다).
