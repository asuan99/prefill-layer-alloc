# PLAN — 128k 프로브 (long-ctx 블록 적용 가능성 확인, 2026-10-20, main) — 계획만, 미실행

> 지위: Workspace bring-up 프로브 계획이다(운영 모델 §1-1: 측정은 Job만, Workspace는 bring-up·프로브 전용). **나오는 수치는 인용 금지이고, 설계·예산 입력으로만 쓴다.**
> 근거: 설계 `DESIGN_cap_longctx_v1_2026-10-19.md` v1.1 · 결정 12 · 길이 실측 `longctx_stats/LONGCTX_STATS_2026-10-20.txt` · 기존 프로브 `scripts/vessl/substrate_probe.sh`(B4 부팅 8–20분 기준).

## 1. 이 프로브가 가르는 것 (go / no-go)

| ID | 질문 | 실패하면 |
|---|---|---|
| G1 | Nano를 `context_length` 131072, PD-mux, cudagraph ON으로 부팅할 수 있는가 | long-ctx 블록 상한을 낮춘다 |
| G2 | PD-mux는 chunked prefill을 강제로 끈다(-1). 그래서 **장문 prefill 하나가 통째로 한 forward에 들어간다**. 이때 활성화 메모리가 OOM 없이 들어가는가(L ∈ {32k, 64k, 96k, ~124k}) | 해당 L은 PD-mux arm에서 불가 → 격자에서 뺀다 |
| G3 | fused\_sym(chunk -1)·fused\_tuned(chunk 있음)에서도 같은 L이 되는가 | arm 대칭이 깨진다 → 그 L은 제외 |
| G4 | L > 65536이면 span이 1층으로 고정된다(`max(1, 65536 // L)`, 코드 사실 `multiplexing_mixin.py:1658`). 이때 co-resident decode의 ITL이 어떻게 보이는가 | ITL SLO 50 ms가 그 L에서 원리적으로 불가능하면 SLO 설계를 바꾼다 |
| G5 | Llama-3.1-8B를 131072·flashinfer로 부팅하고 같은 L을 처리할 수 있는가. C\_mem(L)이 약 3–20 [유도]인 영역에서 동시 요청이 실제로 들어가는가 | 대조 비교를 32k–64k로 제한한다 |
| G7 | 같은 L에서 합성 고정 길이 입력과 실제 문서(LongBench v1 장문 1–2개, 원본 그대로)의 prefill 시간이 같은가 — "내용 무관" 가정(결정 12′) | 통제 축을 실제 문서 기반으로 다시 설계 |
| G6 | 16k 이후에도 prefill이 L에 선형인가(J1 floor 기울기 0.111 ms/토큰의 외삽이 맞는가) | Job 셀 시간 모형을 다시 만든다 |

★ **입력 + 출력 ≤ 131072 제약**: 출력 4k를 강제하면 입력 상한은 약 126k다. 그래서 "128k" 점은 입력 약 124k로 잡는다(결정 12의 출력 축과 함께 등록할 것).

## 2. 순서와 예상 시간 [유도 — 확정 아님]

| 단계 | 내용 | 자원 | 예상 |
|---|---|---|---|
| 0 | 프로브 스크립트 작성(`scripts/vessl/longctx_probe.sh`, substrate\_probe 형식, 단계별 PASS/FAIL json, `--budget-min` 하드캡) + CPU 회귀 | 로컬 | 에이전트 작업 1회 |
| 1 | Llama-3.1-8B 가중치를 `/data/hf`에 리비전 고정(`0e9e39f2…`)으로 적재. 로컬 HF 토큰을 SSH 표준입력으로 넘겨 `pdmux-build`에서 일시 로그인 → 다운로드 → 즉시 logout(결정 12′) | CPU Workspace | 15–30분 |
| 2 | `pdmux-probe` 재개, 엔진 트리가 merge 트리(manifest sha)인지 확인 | A100 | 5–10분 |
| 3 | Nano PD-mux(agnostic) 부팅 → G1·G2·G4·G6: L ∈ {16k, 32k, 64k, 96k, 124k} 단일 요청 ×2, 장문 prefill 1개와 짧은 decode 4개 동거 | A100 | 부팅 8–20 + 프로브 10–15 |
| 4 | Nano fused\_sym 부팅 → G3(같은 L 단일 요청) | A100 | 부팅 8–15 + 5 |
| 5 | Llama 부팅 → G5·G6: 같은 L 단일 요청 ×2 + C\_mem(L)개 동시 | A100 | 부팅 8–15 + 10–15. 124k 단일 prefill만 약 0.5–1분 [유도] |
| 6 | 결과를 회수하고 Workspace를 즉시 pause | A100 | 5분 |

- **GPU 시간 합계: 약 60–100분 [유도]**이며 `--budget-min 120` 하드캡을 둔다. 사람이 해야 하는 일(1단계 토큰 로그인)과 스크립트 작성을 합치면 **반나절 안팎**이다.
- 시간이 가장 불확실한 곳은 부팅이다(flashinfer JIT 캐시, cudagraph 캡처, 18 GB 적재 — substrate\_probe B4 기준 8–20분). 그다음은 장문 prefill이 선형이 아닐 경우다.
- fused\_tuned(G3 후반)는 G0 튜닝 argmax config가 정해져야 하므로 이번에는 **chunk 2048/8192 중 하나로 대리 확인**만 한다. 정식 확인은 PREREG의 preflight에서 한다.

## 3. 하지 않는 것
- 성능 판정이나 λ\* 측정은 하지 않는다. 나온 TTFT·ITL은 기술값이고 인용 금지이며 Job 예산 입력으로만 쓴다.
- I-5 계측은 넣지 않는다(엔진 트리 미동기화). G0 계측 패치는 따로 진행한다.
- ±10% 구간 선별안과 목표 길이 절단은 쓰지 않는다(결정 12′). 프로브 입력은 합성 고정 길이이고, G7에서만 LongBench v1 원본 장문을 쓴다(v1 최대 약 69k이므로 G7은 ≤64k 점에서 한다).

## 4. 승인 지점
1. 1단계 CPU Workspace 재개(토큰은 로컬에서 자동 전달, 값은 출력·저장하지 않음).
2. 3–6단계는 A100 Workspace를 재개해야 하므로 사용자 승인이 필요하다. 실행 명령과 하드캡을 먼저 보여 준다.
