# 7-8B 스케일업 — decode-SM 스윕 결과 (정본 아님, claims-auditor 선행 필요)

2026-07-27~28. jobs 865289/865297/865305(스모크·backend 대조), 865311/865312(v1),
865493(v2), 865533(v3). 분석 = `s8_analyze.py`(실현 파티션 귀속) +
`s8_batch_matched.py`(파티션×batch 동시 매칭).

`s0_deconfound/DESIGN.md` §5 사전등록이 계속 적용된다 — **정본 수정 금지**.

## 0. 한 줄

파티션·batch·노출을 모두 통제하면 **7-8B decode는 SM에 명확히 민감하다: prefill을 16 SM에
고정한 채 decode만 16→92로 올리면 2.4–2.9×, 그리고 이 값은 4개 arm(pure-Mamba2 /
pure-Transformer / additive hybrid / substitutive hybrid)에서 사실상 동일하다.** 모델 계열
차이는 SM 민감도가 아니라 **절대 비용**에서 나타난다.

⚠️**인용 시 SM16→SM92를 쓸 것.** SM108(=np)은 decode SM만 늘어난 조건이 아니라
**분할 자체가 없는 조건**이라 prefill 할당도 16 SM→무제한으로 같이 바뀐다. 초판이
헤드라인으로 쓴 SM16→SM108(2.5–3.1×)은 두 축이 동시에 움직인 값이다.

★**이 측정의 지위(오독 방지)**: de-confound 설정은 `[prefill, decode, idle]` =
`[16,16,76] / [16,24,68] / [16,44,48] / [16,92,0]`으로, 저-D 셀은 **SM 대부분을 일부러
놀린다**. 즉 이것은 **decode 쪽 등량곡선**이지 정책 비교가 아니다 — 실제 정책에서는 decode가
안 쓰는 SM을 prefill이 가져가므로 `prefill_SM + decode_SM ≤ 108` 제약이 걸린다.
따라서 본 결과는 **레버의 존재**만 확립하며, **레버를 움직여 서빙 goodput이 나아진다는
근거가 아니다**(정본 방법론 게이트 #1). 정책 판단에 필요한 대상은 프론티어
**ITL(D) vs TTFT(108−D)** 이고 그건 미측정이다. 또한 정본의 실패 기전(얽힘: decode 굶김→
ITL↑→batch 정체→prefill admission 차단→TTFT 폭발)은 decode-ITL 지표에 원리상 보이지 않는다.

### 2.1 판정

- **decode SM 민감도는 실재하고 모델-무관이다.** pure-Mamba2(2.7–3.0×)가 pure-Transformer
  (2.6–2.8×)와 구분되지 않는다 ⇒ "SSM decode는 O(1)이라 SM-bound 불가"라는 **음성대조 전제는
  틀렸다**(O(1)은 context 길이에 대한 것). `s0_deconfound/FINDINGS_865098.md` §4의 **(b)**가
  두 번째 스케일·다른 모델·batch 통제 하에서 확인됐다.
- **"hybrid이 급락한다"는 hybrid의 성질이 아니라 Zamba2 계열(additive)의 성질이다.**
  matched batch·SM에서 **Hs8(substitutive)/M8 = 0.86**(즉 pure-Mamba보다 **빠르다**),
  **Ha8(additive)/M8 = 1.57(SM16) ~ 1.69(SM108)**. Zamba2는 mamba 스택을 대체하지 않고
  그 위에 shared attention(concat 2×hidden, MHA 32×160, MLP 10240, LoRA adapter)을 **더하는**
  구조라 per-token 비용이 상위집합이며, 1차 weight-traffic 추정(M 5.40 / T 6.17 / H 7.66 GB)의
  1.42×와 같은 자릿수다.
- **Ha8의 SM 민감도는 오히려 최저(2.54–2.75×)** — 1차 미통제 수치가 준 "Zamba2가 가장
  SM-민감(4.44×)"은 **아티팩트**였다(활성률 최저 + batch 공변).

## 3. ★철회 — "공간 분할이 시간 공유를 3.2× 이긴다"

2026-07-27 중간 보고에서 NP(무분할) 셀이 d92보다 3.2× 느리다는 이유로 그렇게 적었다.
**batch 통제 후 무너진다**: 그 격차는 NP 셀의 decode batch가 12–16이고 d92가 3.7이었던
탓이다. matched batch에서는 SM108(무분할)이 SM92(분할)보다 **오히려 근소하게 빠르다**
(M8 b4: 15.12 vs 16.15 · T8 b4: 10.78 vs 12.13) — SM이 더 많으니 당연한 방향이다.
⇒ 이 데이터는 PD-mux의 공간 분할 이득에 대해 **아무 말도 하지 않는다**(그 질문은
prefill TTFT까지 같이 봐야 하며 여기선 측정하지 않았다).

## 4. 하네스 결함과 수정 (전부 이번 캠페인에서 발견)

1. **Codestral 로더**: transformers식 `backbone.embeddings.`(복수형) 키를 기존 로더가
   버려 **랜덤 임베딩으로 서빙될 뻔했다** → `src/models/mamba2.py` 매핑 추가.
2. **파티션 활성률**: green-ctx 분할은 split-prefill 동거 중에만 유효하고, 비면
   `adjust_stream_groups`가 무분할 (0,108)로 되돌린다. v1에서 활성률 **13–93%**.
   ⇒ 셀 평균은 D와 108의 혼합이며, 활성률이 D와 상관(coupled: d16 0.128 vs d92 0.774)해
   **D축이 다시 오염**된다. 대응 = 구간 귀속 분석(§2).
3. **decode batch 공변**(865098 §2 재발): ctx4096서 7.5→3.7, NP 15.2.
   ctx1024로 prefill feed를 빠르게 하면 10.8–12.7로 안정. 최종 분석은 batch까지 매칭.
4. **클라이언트 시간 원점**: `s0dc_client.py`의 `chunk_times_s`는 **상대시간**인데
   telemetry는 절대 monotonic이라 귀속이 **조용히 0건**이 됐다 → 클라이언트에
   `t0_monotonic_s` 기록 추가. (Stage 0 클라이언트는 절대시간이라 그대로 이식한 게 원인.)
5. **v3 가설 반증**: "keepalive 프롬프트를 길게 하면 duty cycle이 오른다"는 **틀렸다** —
   활성률이 0.66–0.93(v2, 짧은 프롬프트×8 worker)에서 **0.32–0.63(v3, ~2000토큰×4)** 로
   떨어졌다. 긴 prefill 윈도우 동안 decode가 진행되지 않아 둘이 시간적으로 분리된다.
   ⇒ 활성률을 올리려면 **짧은 prefill을 자주** 넣어야 한다.

## 5. 한계 (인용 시 필수)

- ctx **1024 한정**(귀속 가능한 유일 데이터셋 — ctx4096 셀은 클라이언트 패치 이전이라 원점 부재).
- Hs8만 flashinfer(+2.3% offset, §1).
- `--disable-piecewise-cuda-graph`, `--disable-overlap-schedule`, `--chunked-prefill-size -1`,
  `--disable-radix-cache`, `max-running-requests 48`, A100 80GB 1장, TP1.
- 이 결과는 **decode ITL의 SM 스케일링**만 말한다. goodput·TTFT·정책 비교는 측정하지 않았다.
- 파티션 활성률이 100%가 아니므로 각 SM 버킷의 표본은 **그 파티션이 실제 활성이던 구간**에
  한정된다. 활성 구간이 비활성 구간과 체계적으로 다른 상태(예: 항상 prefill 동거 중)라는
  점은 남아 있는 미통제 요인이다.
