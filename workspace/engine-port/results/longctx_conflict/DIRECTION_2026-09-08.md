# 방향 판정 — (ㄱ) 축소 L−2 vs (ㄴ) L1 직행(ITT)

2026-09-08 · **GPU 0** · 이 문서는 **어느 것을 살 것인가**만 정한다. 정책 판정 0건.

---

## 1. ★먼저 자기 정정 — (ㄱ)의 비용 기각은 **제 등록 부하 탓**이었다

앞서 (ㄱ)을 *"수십~100+ GPU-hr에 payoff는 레버 존재 확인 하나 ⇒ 비용/효용 불일치"*로
기각했다. **그 근거를 실측으로 재보니 기각의 원인이 설계가 아니라 `PREREG_L2_REV2 §3.5`가
등록한 부하였다.**

Stage 0 실측(텔레메트리 span, 부팅·모델로드·캡처 제외):
**36셀 합계 1.69 h**, 셀당 평균 **2.8분**(3 rep 포함) — ctx별로
`H` 1.4 / 2.9 / **6.7분**, `T` 0.8 / 1.6 / 3.8분.

| 판본 | 셀 | 부팅 | 부하 배수 | 추정 |
|---|---|---|---|---|
| **Stage 0 부하 유지** + n≥4 부팅 | 27 | 108 | 1× | 벤치 ≈ 1.7 h + 부팅 108회 ⇒ **≈ 10–12 GPU-h** |
| **rev2 §3.5 등록 부하**(출력 256 = 8× · 요청 64 = 2×) | 27 | 108 | **16×** | 벤치 ≈ 27 h + 부팅 ⇒ **≈ 33–40 GPU-h** |

⇒ **"100+ GPU-hr"는 제 추정이 아니라 감사의 상한 괄호였고, 실측 기준은 10–40 h이며
그 4배 차이는 전적으로 제가 등록한 부하 파라미터가 만든다.** (ㄱ)의 비용 기각은
**철회**하고, 아래 §3의 **payoff 기준**으로 다시 판단한다.

## 2. (ㄱ)이 여전히 사지 못하는 것 — 비용이 아니라 **질문**

감사 **2F9**는 이 발견들과 무관하게 유효하다: **decode-only + prefill 유휴 + sticky는
PD-mux 운영점이 아니다**(멀티플렉싱할 prefill이 없다). 따라서 (ㄱ)이 답하는 것은
*"long-ctx에서 decode-SM 레버가 **성분으로** 존재하는가"* 뿐이고,
거기서 *"HE0가 ctx-무관으로 강화"*를 도출할 수 없다 —
정본이 이미 같은 형태를 막아 뒀다(`[[scale-8b-sm-sensitivity]]`:
*"레버 존재만 확립, 정책 이득 아님, **HE0 안 되살림**"*).

★그리고 [`FINDING_BIN0_2026-09-08.md`](FINDING_BIN0_2026-09-08.md) 이후,
(ㄱ)이 세우려던 **실현 게이트 자체가 계측 수리를 선행 요구**한다
(`E1_DECODE_REALIZED`의 구간 부과 규칙 · 표본화율). ⇒ (ㄱ)은
**"계측 수리 → 성분 확인"** 두 단계이고, 그 끝에도 정책 진술이 없다.

**판정: (ㄱ)은 죽지 않았으나 우선순위가 아니다.** 살 가치가 생기는 조건은 하나 —
**(ㄴ)이 ctx 상호작용을 보이고 그 기전을 SM 축으로 귀속하려 할 때**의 성분 대조로서다.

## 3. (ㄴ) — **L1 직행, ITT 채점**

### 3.1 무엇을 묻나 (원 질문에 가장 가까운 형태)
> **long-ctx에서 최적 static split 위치가 움직이는가?**

이것은 `CONSENSUS §5-6`이 long-context 전환의 stake로 **첫 번째로 명시한 항목**이다
(*"실제 stake = **최적 static 위치** · 얽힘 병목의 KV 재편 · HE0 반전(혼합 trace에서만)"*).
HE0 반전은 **L3(혼합 trace)** 소관이고 이 단계가 아니다.

### 3.2 ★왜 ITT인가 — 12연속 `NO-GO`가 때린 자리
지금까지의 설계는 **per-protocol**이었다: *"처방대로 실현된 셀만 채점, 아니면 정지"*.
그런데 **비순응(realized ≠ target)의 원인이 처치 자신**이다(SM 분할이 prefill/decode
경합을 바꾼다) ⇒ 처치 이후 변수로 조건화 = collider.

**ITT**: 노출은 **목표 설정값**, 결과는 서빙 지표, `realized`는 **기술 공변량으로 병기**
(게이트 아님). ⇒ 실현 게이트가 필요 없으므로 `bin0`·표본화율·`0.90 vs 0.95`가
**판정 경로에서 사라진다**(전부 병기 항목으로 강등).

★**선례**: **HE0 자신이 ITT다** — `d44 3.220 > bind+GATE 3.132`는 *설정된 정책*의 비교이고
아무도 거기서 realized를 게이트로 걸지 않았다.
⚠️단 *"HE0가 ITT다"* 는 **정본의 자기 규정이 아니라 이 문서의 독해**이며 감사 대상이다.

### 3.3 설계
| 인자 | 값 |
|---|---|
| 노출(처치) | **목표 split** `decode_sms ∈ {16, 44, 92}` — **설정값**, 실현 검증 없음 |
| ctx | 4096 · 8192 · 16384 |
| arm | **`H`(Zamba2-2.7B) 우선 1개**. `M`·`T`는 ctx 상호작용이 관측된 뒤 확장(비용 3× 절감) |
| 부하 | **서빙 부하 — prefill이 실제로 돈다**(2F9 해소). rate 축 포함, 도착 과정 등록 |
| 결과 | **§4.3의 등록 처방 그대로**: Primary = **절대 class SLO + SLO-scale sweep** · Secondary = **prefill-normalized slowdown**(`관측_TTFT / prefill_floor(L)`) · ★`prefill_floor`는 **반드시 실측**(모델링 금지) |
| 병기(게이트 아님) | 셀별 `E1_DECODE_REALIZED` · realized decode batch size · ITL **p50·p95**(게이트 #74) |
| 반복 | n≥4 부팅/셀(게이트 #3), **job-내 split 루프**로 노드 페어링 |
| 추정량 | paired t-CI primary, `level` 명시 · `m`은 **아래 결정 규칙이 요구하는 검정만** |

### 3.4 결정 규칙 — ★**순위 질문**이라 추정량 결함에 강하다
1차 판정량 = **ctx별 argmax split의 위치**. 판정:
- `ARGMAX_MOVES` — argmax가 ctx에 따라 다른 split으로 이동(부트스트랩 아닌 **부팅 간 재현**으로 확인)
- `ARGMAX_STABLE` — 전 ctx에서 같은 split
- `ARGMAX_UNRESOLVED` — 인접 split 간 구분 불가

★**왜 이 형태인가**: 크기 주장이 아니라 **순위 주장**이다. 이 저장소에서 순위는
크기보다 훨씬 견고했다(§1-32: *"magnitude는 ill-posed(metric cliff)나 순위는 견고"*).
그리고 **동등성 형태가 아니라 존재/위치 형태**라 게이트 #94의 보수성 비용을 안 낸다.

### 3.5 이 설계가 **주장하지 않는 것** (선언)
- **HE0를 건드리지 않는다** — static 대 static이지 dynamic 대 static이 아니다.
- **"PD 분리 자체" 귀속을 열지 않는다**(Gate 2 소관, 불변).
- **disjointness를 묻지 않는다**(L3s 소관 — 그건 전칭 명제라 훨씬 비싸다).
- **실현 할당에 대해 아무 주장도 하지 않는다**(ITT의 대가 — 이건 기능이지 결함이 아니다).
- *"장문에서 PD-mux가 decode를 보호한다"* 로 승격하지 않는다(승격 금지 승계).

### 3.6 비용
`H` 단독 = 3 split × 3 ctx × n4 = **36 부팅**. Stage 0 실측 기준 벤치 ≈ 0.6 h + 부팅 36회
⇒ **≈ 4–6 GPU-h**(부하를 Stage 0 수준으로 유지 시). `prefill_floor` 실측 선행 별도.
arm 확장 시 3×.
